# Judge 2 — reuse ladder, cross-platform, lock-in, maintenance

## 1 Method

All three proposals were present and read in full. I scored each proposal's *endorsed architecture* (A = O2 `ats` over the ClawTeam CLI; B = O7 independent Core with two seams and two coordination substrates; C = O2+O3 composed as a library over ClawTeam's Python seams with an in-process `SpawnBackend`, plus O5 PRs filed-not-depended-on) on R1–R10, citing evidence files, the fit-gap matrix and the reuse-vs-build table rather than the proposals' own claims. Where a proposal made a mechanism claim I could check, I re-read the ClawTeam source read-only: `ClawTeam/clawteam/spawn/adapters.py:49-53,131-140`, `ClawTeam/clawteam/spawn/subprocess_backend.py:80,151-152`, `ClawTeam/clawteam/cli/commands.py:3251-3262`, `ClawTeam/skills/clawteam/SKILL.md` (269 lines) + `references/*.md` (401+207 lines), and `gh pr view 82|88` + `gh api repos/HKUDS/ClawTeam/commits?per_page=1` (HEAD `0119833`, 2026-05-09). My lens weights R2/R3/R5/R8/R9: the proposal that stays smallest *and* still works if ClawTeam stays dead or a harness CLI renames a flag.

## 3 Per-proposal critique

### Proposal A — ClawTeam maximalist (O2 `ats`)

**Strengths.** The smallest credible scope; honest §8 shows exactly where O1 fails (AD-02/05/07, TC-05, TE-07, HB-01/03/05/07, EV-02/03, AR-01/02/03) [fitgap:AD-01][fitgap:HB-01][fitgap:EV-03]; every ClawTeam trap is named with probe evidence (child-becomes-leader, `task wait` default inbox, cleanup leaves processes, DEVNULL, `exit_code: null`) [ev:clawteam-probe-log#F18][ev:clawteam-model#F8][ev:clawteam-probe-log#F20][ev:clawteam-probe-log#F12][ev:clawteam-probe-log#F14]; CLI-only coupling keeps the implementation language open; the 269+608-line Skill claim is correct (verified by `wc`). Its ranking O2 > O1 > O7 > O5 is consistent with the reuse table ("rung 3 is never the only path", 23 rung-6 gaps are data objects) [reuse §2].

**Factual errors / imprecisions.**
1. "Passing an explicit positional command bypasses ClawTeam's adapter chain and profile inference [F5][F11]". Only the profile half is right. `SubprocessBackend.spawn` still calls `self._adapter.prepare_command(...)` on the explicit command (subprocess_backend.py:80); an unrecognised basename falls into the generic branch and gets `-p <prompt>` appended when a prompt exists (adapters.py:139-140) [ev:clawteam-probe-log#F12], and `os.getuid()` is evaluated before any basename check whenever `skip_permissions` is true (adapters.py:53) [ev:clawteam-spawn-platform#F20]. The net effect A wants (renderer decides the harness argv) holds only because the wrapper's basename is unrecognised *and* A sets `skip_permissions=false`.
2. Windows: "the wrapper delivers prompts by file … to dodge cmd.exe newline truncation". The harness prompt, yes; but when `ats` passes `--task` to `clawteam spawn`, ClawTeam's own multi-line `## Identity/## Task/## Coordination Protocol` prompt is still appended to the argv by the generic branch and goes through `list2cmdline … & exit_hook` on Windows — exactly the truncation PR #159 reports [ev:clawteam-spawn-platform#F20]. The fix is cheap (see §5 amendment 2): spawn without `--task`, since `commands.py:3251-3255` builds the prompt only when `task` is given and the generic branch appends `-p` only `elif prompt:`.
3. O2 size "≈3–4k LOC" vs its own table ≈4.35k before tests. Minor.
4. R4 = 5 "all eight walk through cleanly" ignores that `team status`/`board show` list hidden Members [ev:clawteam-probe-log#F10], that the dynamic-member gate is bypassable by a Lead shelling `clawteam spawn` (no gate on the CLI path) [ev:clawteam-spawn-platform#F16], and that the nested result carrier is unverified with real agents [ev:clawteam-probe-log §5 q3]. These are the same residuals C lists as hacks; A's number is a self-grade, not an error.

**Coverage gaps.** TC-05 enforcement-bypass unflagged (C §9 flags it; B is also silent). Member-side coupling: Leads/Members are told to use `clawteam task/inbox` by ClawTeam's own Skill — if the substrate is swapped, every Assistant/Team bundle's coordination section changes; A does not call this out as lock-in. Archive reading parses ClawTeam's internal directory layout (`config, spawn_registry, events, inboxes`, `tasks/<run>`) rather than CLI `--json` output — that is tighter coupling than "CLI only". The ensemble-synthesis harness choice and `cost_source: derived` for Codex are left to the broker model's open questions without a PoC decision [model:harness-broker-model#13].

### Proposal B — independent thin layer (O7)

**Strengths.** The clearest ownership model: two narrow seams (HarnessAdapter = profile data + recipe + invoke + parse [model:harness-broker-model#10]; CoordinationSubstrate = create/add/task/wait/send/snapshot/cleanup) and an explicit statement of what is *not* reused from ClawTeam (`launch`, adapter chain, keepalive, plugins) [ev:clawteam-probe-log#F15][ev:clawteam-probe-log#F23][ev:clawteam-spawn-platform#F6]. Its `direct` substrate is the cleanest tmux-free, shell-free Windows path for PoC A and matches A's own O7 evaluation ("direct-CLI backend with file prompts is the cleanest Windows path"). Hermes is weighed correctly: strong harness target (`-z --usage-file`, profiles, distributions), not a team backend (kanban Hermes-only and un-nestable; delegation children cannot target other harnesses) [ev:claude-agent-teams-hermes-openbot#F22][ev:claude-agent-teams-hermes-openbot#F25][ev:harness-cli-capabilities-b#F19]. Its §8 is the most candid about "multiple backends is thinner than the slogan" [ev:claude-agent-teams-hermes-openbot#F2][#F7][#F8][ev:openclaw-native-and-telegram-verification#F16].

**Factual errors / imprecisions.**
1. Size accounting is inconsistent: the §4 table sums ≈11.6k, the headline says "M (6–7k PoC core; 9–11k full)", and §8.1 calls the seam + `direct` backend "~1.5–2k" while the table lists them at ~0.8k. By the rubric the full layer is L, so R1 should be 2 not 3.
2. Mis-citations: the `task update --metadata` open question is [ev:clawteam-probe-log §5 q3], not F20; "snapshot survives cleanup" is [ev:clawteam-model#F22 step 12]/[ev:clawteam-probe-log#F20], not F28 (F28 describes the snapshot *record*). `--append-system-prompt-file` is documented and present in the binary but absent from `claude --help` [ev:harness-cli-capabilities-a#F2] — "docs+help" overstates by one notch.
3. Same Windows caveat as A on the ClawTeam path: the launcher "accepts ClawTeam's appended `-p <prompt>` as the coordination section" — that is the cmd.exe argv path. B's §6 claim that prompts travel by file holds for the `direct` substrate only.
4. R8 = 4 ("drift isolated to adapters") is generous: B §8.4 concedes five adapters are the same drift burden O2 carries; the seam does not reduce harness drift, only substrate drift.

**Coverage gaps.** TC-05 bypass unflagged (same as A). Nested result return across per-run `CLAWTEAM_DATA_DIR`s: B proposes separate data dirs for mechanical isolation (§5.3) and then writes the RunResult into the *outer* task and inbox (§5.4) — feasible only via the global `--data-dir` flag [ev:clawteam-probe-log#F2]; unstated. Member-side ClawTeam-Skill coupling acknowledged only in passing. The `direct` substrate "Core-sequenced, no DAG" cannot host PoC B/C, so for the three PoCs B is as ClawTeam-dependent as A — its independence is insurance, not present capability (B §8.3 says so).

The in-process `SpawnBackend` is a real Windows advantage: it never reaches `adapters.py:53` and never puts a prompt on the argv. The `CLAWTEAM_BIN` shim for TC-05 is the only concrete bypass mitigation in the panel. Hermes treatment in O6/O7 is explicit and correct (distribution.yaml as pattern; kanban dispatcher argv as headless worker form; `profile_distribution.py` Hermes-coupled, pattern only) [ev:claude-agent-teams-hermes-openbot#F24][ev:harness-cli-capabilities-b#F19].

"registered as a ClawTeam `SpawnBackend` … so ClawTeam's registry/liveness still see the process" — only if the custom backend calls `registry.register_agent` itself; the built-in backend does so inside `spawn()` (subprocess_backend.py:151-152) [ev:clawteam-spawn-platform#F10]. ## 4 Reuse-ladder & cross-platform check

**Ladder discipline.** The reuse table is unambiguous: rung 1 for TE-01/02/03/06, rung 2 for TE-05/TE-07/HB-02/HB-05 mechanics, rung 6 for 23 data objects, rung 3 "never the only path", rung 5 never [reuse §2]. A sits exactly there (rung 1/2 over the CLI; rung 6 objects) — its R9 5 is earned. B adds a second-substrate seam and a `direct` launcher; the seam is cheap and the launcher trivial, but the *principle* (build the abstraction when the second implementation is demanded) is bent — R9 4. C sits at rung 2 but on the seam with no stability promise when the probe-verified CLI seam satisfies the same M rows, and files rung-3 PRs it admits are "documentation of intent" — R9 3. None reaches for rung 4 beyond `platform_compat.py`/`model_resolution.py` (stdlib, MIT, 200 lines) [ev:clawteam-openclaw-fork-delta#F28] or rung 5, which is correct [reuse §3].

**Cross-platform honesty.** All three say TE-08 is documented, not demonstrated, and that no candidate has Windows CI [ev:clawteam-spawn-platform#F20][ev:clawteam-openclaw-fork-delta#F25] — good. Differences: (a) A and B's ClawTeam path still pushes ClawTeam's coordination prompt through cmd.exe argv whenever `--task` is used (adapters.py:139-140; commands.py:3251-3255); fixable by spawning without `--task`; (b) B's `direct` substrate and C's in-process backend avoid the argv prompt and (C) the `os.getuid()` call entirely; (c) all three need `skip_permissions=false` on Windows if any ClawTeam-built argv is used; (d) macOS is CI-covered for ClawTeam unit tests only [ev:clawteam-spawn-platform#F20]; (e) keepalive is POSIX-only and correctly unused by all three (fresh-by-default). Hermes/OpenClaw/Claude/Codex/Grok Windows support is vendor-docs-only for everyone [ev:harness-cli-capabilities-a#F14][ev:harness-cli-capabilities-b#F16][ev:harness-cli-capabilities-b#F22].

**Survival if ClawTeam stays dead.** ClawTeam is already dormant (no commit in Jun–Aug 2026) [ev:clawteam-spawn-platform#F24], so the risk is bit-rot (the unpinned `mcp` already broke `clawteam-mcp` [ev:clawteam-probe-log#F1]) and unfixed bugs, not drift. Pinning `0.3.0@0119833` + `mcp<2` + uv 3.11 is a frozen dependency; all three tolerate that for 12 months. Replacement cost if it must go: A rewrites a ≈600-LOC compiler plus its archive reader and the Member coordination text; B swaps one CoordinationSubstrate implementation plus the same Member text; C re-implements a Python ABC and replaces imports (or vendors `store/file.py`+`transport/file.py`, rung 4). B < A < C on reversibility; A < C < B on code to maintain.

**Survival if harness CLIs rename flags.** Identical burden: five renderers/adapters in every proposal; ClawTeam's adapter chain is deliberately not relied upon by any of them (it drops the system prompt for 8 of 10 CLIs and has no Hermes/Grok branch) [ev:clawteam-spawn-platform#F1][ev:clawteam-spawn-platform#F2]. B alone names a mitigation (`--help` smoke test + verification levels on profile rows); A's "profiles as data" and C's C3 are equivalent in shape.

## 5 Endorsement + amendments

**Endorsed: a named composition — "A's O2 scope with B's two seams declared; C's PR set filed as good citizenship; C's in-process SpawnBackend kept as the documented Windows fallback."** A is the smallest layer that satisfies the M rows at the lowest rung; B's seams cost little and are the reversibility insurance my lens demands; C's contributions that survive are its honesty list, the `CLAWTEAM_BIN` shim and the observation that in-process spawning is the cleanest Windows route on ClawTeam.

Required amendments (concrete; each changes a document or a PoC pass criterion, none adds a second substrate):

1. **Declare the seams in A's component table on day one.** HarnessAdapter = {HarnessProfile data, injection recipe, invoke, parse} [model:harness-broker-model#10]; CoordinationSubstrate = {create_space, add_member, create_task/update/wait, send/receive, snapshot, stop, cleanup}. One implementation each: the five harness adapters and the ClawTeam-CLI substrate, plus the trivial `direct` launcher (no DAG) for solo invocations / PoC A. No second team substrate until a mixed-harness, nested run is demonstrated elsewhere (C §1).
2. **Never pass `--task` to `clawteam spawn` from the layer.** Put ClawTeam's coordination section into the file bundle the wrapper reads; `commands.py:3251-3255` builds the ClawTeam prompt only when `task` is given and `adapters.py:131-140` appends `-p` only `elif prompt:` — so no multi-line argv on any OS. Keep `skip_permissions=false` in the layer-written ClawTeam config (adapters.py:53). This is the precondition for claiming a Windows path at all.
3. **TC-05 honesty.** State in `architecture-options.md` that the dynamic-member gate is bypassable by a Lead calling `clawteam spawn` (no gate on the CLI path [ev:clawteam-spawn-platform#F16]); adopt C's run-scoped `CLAWTEAM_BIN`/PATH shim that refuses `spawn` inside a run, and reconcile `spawn_registry.json` against the roster after the run (post-hoc audit).
4. **Two rosters accepted for the PoC, stated as such.** PoC B's "user-facing member list" = the layer's views, not ClawTeam's board [ev:clawteam-probe-log#F10]; file the `TeamMember.hidden` PR (reuse §5) but do not wait for it.
5. **Nested result carrier.** Implement both `task update --metadata` and `inbox send <outer> <member>` in PoC C and settle [ev:clawteam-probe-log §5 q3] on the first run; record `independence.achieved: advisory|mechanical` per [model:team-execution-model#6]; if per-run `CLAWTEAM_DATA_DIR` is used, cross-run writes go through the global `--data-dir` flag [ev:clawteam-probe-log#F2].
6. **Generate the Member coordination section per substrate** (task/inbox verbs rendered into the bundle) rather than copying ClawTeam's `SKILL.md` into Assistant/Team definitions — otherwise a substrate swap edits every definition (AD-05/AD-08 spirit; the lock-in none of the three prices).
7. **Read ClawTeam state through CLI `--json` and `team snapshot`**, not the `teams/<run>/*` layout; the only internal file the layer may read is `spawn_registry.json` (pids for stop-before-cleanup [ev:clawteam-probe-log#F20]). List every touched path in the architecture document.
8. **Keep the layer CLI-coupled so the language decision stays open**; the in-process `SpawnBackend` (C4) is adopted only if (a) Python is chosen and (b) the Windows probe shows the CLI-spawn path failing.
9. **PoC-A-first slice** (ATM R5 [model:legacy-atm-disposition#4]): closed schemas + overlay resolver + two adapters (claude-code, codex) + broker + launcher/record + Ensemble record — nothing else until Run 3 passes; run layer after that; operational mode and proposals after PoC C.
10. **Windows/macOS probe as a named PoC-plan task** before TE-08 moves from "documented" to "verified": one headless invocation per harness + one `clawteam spawn subprocess … -- <wrapper>` with `skip_permissions=false` and no `--task` [fitgap:TE-08].
11. **Harness-drift routine**: per-adapter `--help` smoke test and verification levels on every HarnessProfile row (B §7), re-run on each CLI version bump; this is the 12-month maintenance contract.
12. **Pin and freeze**: ClawTeam `0.3.0@0119833`, `mcp<2`, uv Python 3.11; record the pin in the HarnessProfile/substrate record so the archive says which ClawTeam ran each TeamRun [ev:clawteam-probe-log#F1].

## 6 Dissent

A reasonable colleague would still argue: (i) **for B outright** — the seams are not "abstraction before need"; the need is already here because the only team substrate is dormant, and B's `direct` substrate gets PoC A done without installing ClawTeam at all; the extra ≈2k is cheaper than the first forced migration. (ii) **For C's in-process route** — it is the only design in which ClawTeam's registry, liveness and `lifecycle on-exit` see the process *and* the adapter/argv hazards are avoided on Windows; CLI-driving a Python package from another process is the real hack, and since upstream is dead the Alpha seams will never move. (iii) **Against ClawTeam entirely (O6)** — the PoCs need a DAG, an inbox and a pid registry; vendoring `store/file.py` + `transport/file.py` (MIT) removes a dormant dependency with a broken MCP server and a stack of unfixed bugs; ATM's "do not build a mailbox runtime" [ev:atm-salvage#F22] warns against writing one, not against copying 300 lines of one. (iv) **For O1 first** — a one-day ClawTeam template demo would settle the Codex-under-ClawTeam and model-compliance unknowns before any layer is sized. I weigh (i) as the strongest and answer it with amendment 1; (iii) is the fallback if the first PoC B hits a ClawTeam bug the compiler cannot route around.

9. **PoC budget and flakiness tier.** Live-LLM PoCs are flaky/costly (ATM R11); approve a deterministic no-op-harness tier per PoC as the first pass criterion?
10. **Ensemble synthesis harness** for PoC A Run 3 (third harness, one leg, or the Lead's) and the Codex cost derivation rule (`cost_source: derived|unavailable`) [model:harness-broker-model#13].
