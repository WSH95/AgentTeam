# Proposal C — extend ClawTeam upstream-friendly, and build only the layer ClawTeam cannot hold

## 1. Bias statement & what would change my mind

**Bias.** ClawTeam is the only probe-verified substrate that already gives a fresh, mixed-harness, tmux-free TeamRun with a task DAG, inboxes, liveness registry and a snapshot archive [fitgap:TE-01][fitgap:TE-03][fitgap:TE-06][ev:clawteam-probe-log#F16][ev:clawteam-probe-log#F23]. Everything it lacks for our M-priority rows is either (a) a PR-sized delta — `os.getuid` guard, `mcp<2` pin, stdout/exit-code capture, `TeamConfig.created_by`, `TeamMember.hidden`, process-stopping cleanup, Hermes/Grok adapter branches, `launch` error surfacing [reuse:§5] — or (b) a *data object* no substrate has at all (Assistant definition, TeamTemplate-by-reference, overlays/Proposals, HarnessProfile/policy/invocation record, artifact manifest/lock) [reuse:§6]. So the smallest new layer is: **file the (a) PRs, and build (b) as a thin library/CLI that talks to ClawTeam through its existing seams** (`TeamManager`, `FileTaskStore`, `MailboxManager`, `register_backend`/`SpawnBackend`, the event bus, the 26-tool MCP server) [ev:clawteam-spawn-platform#F15][ev:clawteam-spawn-platform#F8][ev:clawteam-model#F21]. I argue O5 + O3 + O2 composed.

**What would change my mind.** (1) Evidence that a second substrate hosts a *mixed-harness, nested* TeamRun without a daemon — none does today: Claude Code teams are Claude-only, interactive-only, non-nested [ev:claude-agent-teams-hermes-openbot#F6][ev:claude-agent-teams-hermes-openbot#F7][ev:claude-agent-teams-hermes-openbot#F8]; OpenClaw has no team object and needs the Gateway for `sessions_spawn` [ev:openclaw-native-and-telegram-verification#F21][ev:harness-cli-capabilities-b#F15]; Hermes kanban is Hermes-only and "cannot spawn a board within a board" [ev:claude-agent-teams-hermes-openbot#F25]; dsh forbids nesting [ev:dsh-agent-teams-and-gui#F26]. (2) Evidence that ClawTeam's Python seams are so unstable that importing them costs more than vendoring `store/file.py` + `transport/file.py` (then O6 wins). (3) A maintainer response on any ClawTeam PR — which would make the PR half of this proposal real instead of aspirational (see §8).

## 3. Ranking with reasons

1. **O2 + O3 composed (library over ClawTeam seams), with O5 filed but not depended on** — my proposal (§4). Smallest code that meets the M rows (R10 4–5) at rung 1/2 for mechanics and rung 6 only for data objects; days to PoC A/B on this host.
2. **O7** — same objects, plus a team-backend abstraction; it is where #1 converges if ClawTeam's seams drift or a second coordination substrate appears (§8). Loses only on R1/R7 today.
3. **O6** — right call for `platform_compat.py`, the model-precedence pattern and Hermes/DG/ATM *shapes*; wrong call for vendoring the task store while `FileTaskStore` works in place.
4. **O2 alone** — PoC B/C viable; PoC A's attribution/record and HB-03 policy missing.
5. **O3 alone** — PoC A clean; nothing for teams/evolution.
6. **O5 alone** — cheapest code, least realistic: R2/R7/R8 all 1 on the upstream evidence.
7. **O1** — fails the PoC pass criteria as stated (hidden member, byte-identical definition with per-harness injection, recorded invocations).
8. **O4** — orthogonal; a C-priority adapter.
9. **O8** — no evidence of necessity; contradicts XC-03.

## 5. Pressure-test walkthroughs

**PoC A — same Assistant on Codex / Claude Code / both + synthesis.** *Mechanics:* `ats run-solo code-reviewer --harness codex` → C2 resolves effective definition (hash h) → C4 renders for Codex (`codex exec -c developer_instructions=<persona+principles> --json --output-schema review.json`, skills symlinked into `$CODEX_HOME/.agents/skills`, `--ephemeral`) and records `inv-1` (tokens, no USD: `cost_source: unavailable`); Run 2 renders for Claude (`claude -p --bare --append-system-prompt-file … --json-schema …`) → `inv-2` with `total_cost_usd`; Run 3 = Ensemble: two legs sharing `bundle_hash`, own cwd each, then a third invocation whose prompt prefix carries both structured outputs labelled by invocation id and whose schema requires `agreements[]/disagreements[]` per id. Definition file untouched by construction (C4 reads, never writes). *New:* C3/C4 entirely; *reused:* harness flags [ev:harness-cli-capabilities-a#F2][ev:harness-cli-capabilities-a#F10][ev:harness-cli-capabilities-a#F19]. *Caveat:* Codex `-c developer_instructions` is observed, not executed; fallback is AGENTS.md in a prepared `CODEX_HOME` [model:harness-broker-model#13].

**PoC B — fresh TeamRun, hidden temporary Member, mixed harnesses.** *Mechanics:* `ats run development --project /repo --task …` → C5 creates ClawTeam team `run-7f3a` via `TeamManager.create_team` (Lead as leader), adds Members, creates skeleton tasks, spawns each via C4 (`register_backend("ats")`, fully rendered command → ClawTeam's implicit profile suppressed [ev:clawteam-spawn-platform#F5]); Lead on Claude Code, Implementer on Codex, Reviewer on Hermes. Lead calls `ats member add migsafe --hidden --from-ephemeral migsafe.md`; C5 checks `dynamic_members` (may_create, count, harnesses) *before* `add_member`+spawn, writes the Ephemeral Assistant into the run dir, marks `visibility: hidden` in the roster. `ats status` filters hidden; `ats archive` shows all. DAG completion via `clawteam task wait` [ev:clawteam-probe-log#F7]. *New:* roster projection, gate, Ephemeral Assistant file; *reused:* spawn/members/DAG [ev:clawteam-probe-log#F16][ev:clawteam-probe-log#F18]. *Hack:* ClawTeam's own `team status`/`board` still lists `migsafe` until `TeamMember.hidden` (C8) merges [ev:clawteam-probe-log#F10] — two views of one roster.

**PoC C — nested TeamRun with result return + archive.** *Mechanics:* CodeMod (a Member of `ops`) calls `ats nest development --for-task t4`; C5 checks `nesting.max_depth`, creates inner run `run-c21d` with `parent: {run: ops, member: codemod, task: t4}`, creates the ClawTeam team with `team spawn-team run-c21d -n codemod` **first** (so CodeMod, not the first child, is the ClawTeam leader — trap 1), then spawns inner Members; marks outer `t4.metadata.delegated_to = run-c21d`; waits with `task wait run-c21d --agent codemod` (trap 2 avoided). Inner Lead ends with `ats result --status completed --summary … --deliverables …`; C5 copies RunResult into `t4.metadata.result`, `inbox send ops codemod` as notification, snapshots `run-c21d`, stops registered inner processes, rmtree, records `nested_runs[]` in the outer `run.json`. *New:* contract + link + cleanup order; *reused:* spawn-team/spawn/wait/inbox/snapshot [ev:clawteam-model#F22][ev:clawteam-probe-log#F19][ev:clawteam-probe-log#F20]. Isolation of inner task/message space is **namespace-only** on ClawTeam (any identity may send to any team) [ev:clawteam-probe-log#F19]; the run layer enforces it only for what it delivers itself — PoC C's "isolated" criterion is met as "not shared by default", not mechanically prevented, until the inbox-ACL PR (C8) merges.

**Nested TeamRun result + archive (contract detail).** RunResult `{status, summary, deliverables[], risks[], archive_ref}` is written by the inner Lead through `ats result`, never by free-text message; the outer task completes only when the inner run reaches a terminal status; inner liveness is watched by C5 via `registry.is_agent_alive` (inner Lead dead + pending tasks → `aborted` → outer `t4 failed`) [ev:clawteam-probe-log#F13][model:team-execution-model#6]. Archive nesting = outer `run.json.nested_runs[].archive` → inner `snap-*.json` + inner ledger. Leak prevention: inner invocations get `--bare`/`--ephemeral`/fresh Hermes profile [ev:harness-cli-capabilities-a#F19][ev:harness-cli-capabilities-b#F19]; nothing writes to any definition (C4/C5 are read-only on `assistants/`).

**Ensemble + synthesis.** As PoC A Run 3; additionally usable for any Member when policy says `ensemble.when: task_type in [code-review]` [model:harness-broker-model#8]. On ClawTeam the legs are two Members with distinct names and cwds (worktrees via `--repo`) [ev:clawteam-probe-log#F22]; attribution comes from the ledger (harness, version, model, cost), not from ClawTeam's self-reported `CostEvent` [ev:clawteam-model#F28]. *New:* Ensemble record, structured verdict, `bundle_hash`. *Hack:* none beyond Codex cost derivation.

**Evolution overlays + Proposals.** After a run, `ats propose --from run-7f3a` reads the archive (findings, Lead corrections, invocation outcomes) and emits typed Proposals (`field`, `append|override|narrow`, provenance runs, independence check, dedupe) into `proposals/`; `ats review` accepts/rejects, appending to `overlays/<assistant>.evolution.yaml` with `applied_hash` [model:assistant-domain-model#9]. ## 6. Cross-platform story

Ubuntu (this host, no tmux): C4's backend spawns directly (`subprocess.Popen` with captured pipes), registers pid in ClawTeam's registry, and never calls `NativeCliAdapter.prepare_command` with `skip_permissions` — so the `os.getuid()` branch is never reached; ClawTeam's tmux backend is not used; `clawteam launch` is not used (it hides tmux failures and applies one profile to all) [ev:clawteam-probe-log#F15][ev:clawteam-spawn-platform#F12]. macOS: identical POSIX paths; ClawTeam CI covers macOS for its part [ev:clawteam-spawn-platform#F20]. Windows: C4 passes prompts and system prompts by **file** (`--append-system-prompt-file`, `--message-file`, `--prompt-file`, `CODEX_HOME/AGENTS.md`) to dodge cmd.exe newline truncation, needs no keepalive loop (fresh-by-default), uses `platform_compat.pid_alive`/`exclusive_file_lock` patterns; ClawTeam's store/transport already have `msvcrt` branches and `os.replace` [ev:clawteam-spawn-platform#F20][ev:clawteam-openclaw-fork-delta#F19]; the harness CLIs document native Windows support [ev:harness-cli-capabilities-a#F14][ev:harness-cli-capabilities-b#F16][ev:harness-cli-capabilities-b#F22]. Host OS and harness presence are recorded per Member as independent dimensions from the HarnessProfile (XC-02). **Not demonstrated:** no Windows/macOS probe exists for any candidate [fitgap:TE-08]; the C8 guard PR makes plain `clawteam spawn` safe on Windows only if merged.

## 8. Where my bias breaks

1. **Rung 3 is not cheaper than rung 2 here.** The re-check on 2026-08-22 shows HEAD unchanged since 2026-05-09 and PRs #82/#88 open since March; "upstream-friendly" therefore buys goodwill, not capability. Every PR in C8 has a rung-2 shadow in C4/C5 — which means the PRs are *documentation of intent*, and the architecture must be judged as if none merges.
2. **"Broker as ClawTeam plugin" is a misnomer.** `register_backend` works only inside the process that registers it; `clawteam spawn` never loads plugins; `BeforeWorkerSpawn` neither fires there nor mutates [ev:clawteam-spawn-platform#F16][ev:clawteam-spawn-platform#F17]. So O3 collapses into "a library that imports ClawTeam", i.e. O2's shape — and the mutation-hook PR I wanted is unnecessary once the broker renders before spawn. I drop it.
3. **The fallback is O7-lite.** If ClawTeam's seams drift, vendoring its store/transport (O6) is the next step, and the run layer then owns coordination — at that point the difference from O7 is only that no second team backend exists. I concede that C5's roster, nesting and ledger contracts should be written substrate-neutral from day one (cheap), while *building* a second team-backend adapter stays unjustified until one can host a mixed-harness nested run (§1).
4. **Hidden/created_by as sidecars leave ClawTeam's own board contradicting `ats status`** — acceptable for the PoC, not for a product; this is the strongest reason to still try upstream (or, failing that, to stop using ClawTeam's board).
5. **ClawTeam's operational primitives fight LO** (resident worker loop, keepalive, "exited unexpectedly" on clean exit): for operational runs ClawTeam contributes registry+archive only; if LO becomes central, Hermes kanban or OS schedulers carry more weight than ClawTeam.
