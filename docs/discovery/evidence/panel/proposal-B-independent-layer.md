# Proposal B — the durable product object lives outside every substrate

## 1. Bias statement & what would change my mind

**Bias.** The product object is a *definition* (Assistant + TeamTemplate + overlays + HarnessProfiles + invocation/archive records). None of it may live inside one execution substrate, because every substrate we measured is harness-shaped: ClawTeam's unit is an inline `task` string per TOML member and a fixed `command` [ev:clawteam-model#F13][ev:clawteam-probe-log#F17]; Claude Code's unit runs only as a Claude session [ev:claude-agent-teams-hermes-openbot#F6]; a Hermes distribution is a Hermes package whose children "cannot target other profiles or harnesses" [ev:claude-agent-teams-hermes-openbot#F22][ev:claude-agent-teams-hermes-openbot#F24]; an OpenClaw agent is identity + workspace + sessions [ev:harness-cli-capabilities-b#F10]. The fit-gap says it plainly: for AD, TC and EV no system reaches ≤ Xs on all M rows, "the layer is genuinely new relative to every substrate" [fitgap:AD-01][fitgap:TC-01][fitgap:EV-02]; 23 of 54 gaps are rung 6 and "most rung-6 items are data objects … not runtime machinery" [reuse:G-XC-03]. So I propose a **small independent layer (the "Core")** that owns definitions, the HarnessBroker (profiles as data, selection precedence, fallback, ensemble, injection bundles, invocation records), the nesting/archive contract and evolution proposals — and treats ClawTeam, direct CLI invocations, Claude Code native subagents, Hermes (profile + kanban) and OpenClaw sessions as interchangeable backends behind two narrow interfaces (a *harness adapter* seam and a *coordination-substrate* seam). I fold in O6 (vendor the stdlib-only fork modules) and O3's idea (the broker as the thing that renders what a spawn backend receives) without making the broker a ClawTeam plugin.

**What would change my mind.** (a) HKUDS/ClawTeam revives (no commit since 2026-05-09, PRs #159/#165/#167 unanswered [ev:clawteam-spawn-platform#F24]) and merges a reusable definition object, `TeamMember.hidden`, `TeamConfig.created_by`, a mutating pre-spawn hook and output capture — then O2/O5 would be roughly half my size. (b) PoC A shows that Codex/Hermes/OpenClaw injection cannot be done per invocation without prepared directories *and* that ClawTeam worktrees are a good enough place for them — then my broker collapses to a prompt renderer and O2 suffices. (c) The owner commits to one harness family for twelve months — the broker's value drops below its cost. (d) Hermes kanban gains cross-harness dispatch (open question 5 in [ev:claude-agent-teams-hermes-openbot]) — Hermes would become the cheaper TE substrate than my run layer over ClawTeam.

## 3. Ranking with reasons

1. **O7 (+O6 sourcing, +O3's rendering idea)** — only option that closes all eight pressure tests and all M rows, keeps the product object out of any substrate format, and scopes ClawTeam to what it is verified to do well (DAG, inbox, registry, snapshot, subprocess spawn on this host [ev:clawteam-probe-log#F7][ev:clawteam-probe-log#F9][ev:clawteam-probe-log#F12]).
2. **O2** — the cheapest credible path and my fallback; it converges on O7 the moment PoC A Run A (Codex) needs a rendered injection bundle, so choosing O2 mostly means deferring the substrate seam.
3. **O6** — right as the sourcing rule for O7/O2 (vendor two stdlib modules; call ClawTeam via CLI; copy Hermes/DG patterns), wrong as a standalone answer.
4. **O3** — correct instinct (the broker owns rendering) in the wrong place (a process that never loads plugins, Alpha seams).
5. **O5** — file the small PRs anyway (they are good citizenship) but plan as if unmerged.
6. **O1** — fails the PoC pass criteria by construction (persona loss on Codex, no hidden flag, no records).
7. **O4** — orthogonal; defer until MS-02 is wanted.
8. **O8** — violates XC-03.

**Explicit exclusions (not built, ever, in this layer):** task DAG, mailbox/transport, worktree manager, process liveness/keepalive, board UI (ClawTeam's; Hermes kanban later); any harness (proprietary or not) — only argv/files; a message bus or router (ATM X1 discarded [model:legacy-atm-disposition#2]); surface adapters beyond the local conversation (C-priority); a GUI; ClawTeam forks; OpenClaw gateway dependence.

**What is reused vs re-implemented from ClawTeam, concretely.** Reused via CLI: `team spawn-team/add-member/status`, `task create/update/list/wait`, `inbox send/receive/peek/log`, `spawn subprocess -- ats-launch …` (registry + pid liveness + `lifecycle on-exit` task reset), `team snapshot/cleanup`, worktrees via `--repo` where wanted, its SKILL.md for Lead/Member coordination. **Not** reused: `launch` (swallows errors, one profile for all, no task edges [ev:clawteam-probe-log#F15][ev:clawteam-probe-log#F23]), the adapter chain/keepalive/session locators as code (their flag knowledge becomes profile data), `harness conduct`, plugins/hooks, `clawteam-mcp` (only if `mcp<2` pinned [ev:clawteam-probe-log#F1]). This is not a second ClawTeam: none of ClawTeam's ~19k lines of coordination is duplicated; the Core adds the objects ClawTeam never had.

**Interfaces (what calls what).** Core → harness CLIs: only through `ats-launch` (direct substrate) or through `clawteam spawn subprocess -- ats-launch` (ClawTeam substrate; the explicit positional command suppresses profiles [ev:clawteam-spawn-platform#F5], the generic branch appends `-p <prompt>` which the launcher consumes [ev:clawteam-probe-log#F12], and the wrapper's `lifecycle on-exit` keeps CT's registry/task reset working [ev:clawteam-probe-log#F14]). Members → ClawTeam CLI for tasks/inbox (its own Skill); Members → `ats member create | ats nest | ats result` for the three gated run-layer operations (identity from `ATS_RUN_ID`/`ATS_MEMBER` env written into the bundle). Core → `git worktree add` only when no substrate provides one. Evolution → broker (the critic is just another invocation).

**Data the Core owns.** `definitions/` (assistants, templates, overlays, proposals, locks — read-only during runs, hash-checked after); `profiles/`; `runs/<id>/` (run.json, members/, bundles/, invocations/ with stdout/usage/exit, nested refs, decision log, archive/); nothing under `~/.clawteam` except a per-run `CLAWTEAM_DATA_DIR` the substrate adapter points at [ev:clawteam-probe-log#F3].

## 5. Pressure-test walkthroughs

**5.1 PoC A — same Assistant on Codex / Claude Code / both + synthesis.** Mechanics: `ats run assistant code-reviewer --target <diff> --harness codex` (direct substrate, no team). Broker resolves (no User Overlay; Assistant-level policy prefers `[codex, claude-code]`; `decided_by` recorded), prepares one bundle {persona+principles text, skills dir, permissions intent, output schema}, `bundle_hash`. Run 1 (Codex): `codex exec --json --output-schema review.json -C <ws> --ephemeral --ignore-user-config -c developer_instructions=<text>` — `developer_instructions` is observed but unexecuted [ev:harness-cli-capabilities-a#F2]; the adapter's fallback is `AGENTS.md` in a prepared `CODEX_HOME` (`degraded: []` vs `degraded: [system-prompt-as-file]` recorded on the invocation). Run 2 (Claude): `claude -p --bare --append-system-prompt-file <f> --add-dir <skills> --output-format json --json-schema review.json` [ev:harness-cli-capabilities-a#F17][ev:harness-cli-capabilities-a#F19]. Run 3: Ensemble record, two legs in separate workspaces sharing `bundle_id`, then a third invocation whose prompt carries both structured outputs labelled by invocation id and whose schema demands `agreements[]/disagreements[]` with ids [model:harness-broker-model#8]. Records: session id/`total_cost_usd` (Claude), tokens only (`cost_source: unavailable`, Codex) [ev:harness-cli-capabilities-a#F10]. Byte-identical check = hash of the definition dir before/after. New: schemas, two adapters, broker, records. Reused: every flag. Verdict: clean; the Codex channel's verification level is the only open item.

**5.2 PoC B — fresh TeamRun, hidden temporary member, mixed harnesses.** `ats run team development --repo R --task T --harness reviewer=codex`. Run layer: resolve three Assistants; broker binds lead→claude-code, implementer→claude-code, reviewer→codex; create `runs/run-X/`; substrate = clawteam with `CLAWTEAM_DATA_DIR=runs/run-X/ct`, `CLAWTEAM_DEFAULT_BACKEND=subprocess`; spawn the Lead first (`clawteam spawn subprocess --team run-X -n lead --agent-type lead --task <coordination text> -- ats-launch inv-01`) — the first spawn creates the team and makes that agent ClawTeam's leader [ev:clawteam-model#F5]; then implementer and reviewer (reviewer with `--repo R` for its own worktree [ev:clawteam-probe-log#F22]); tasks from `workflow_skeleton` via `clawteam task create --blocked-by` (ids validated by the Core, since CT accepts dangling ids [ev:clawteam-probe-log#F7]). The Lead, holding ClawTeam's Skill via `--add-dir`, coordinates with `task`/`inbox`. Mid-run the Lead runs `ats member create --summary … --persona-file … --prefer hermes --hidden`; the Core checks `dynamic_members {may_create:[lead], max_count:3, allowed_harnesses}` before calling the substrate — the gate lives where the spawn call is made [model:team-execution-model#5]; writes the Ephemeral Assistant under `runs/run-X/members/migsafe/`, broker renders `hermes chat --source tool --yolo -q <task> -p <run-profile>` with a cloned profile [ev:harness-cli-capabilities-b#F6][ev:harness-cli-capabilities-b#F19], spawns via CT, roster records `visibility: hidden, origin: ephemeral, policy_decision`. `ats run status` filters hidden; `ats run archive` lists all. DAG completion via `clawteam task wait run-X --agent <core-observer>` (explicit `--agent` avoids draining the leader inbox [ev:clawteam-model#F8]). New: run layer, gate, roster projections, launcher. Reused: CT team/task/inbox/registry/on-exit/snapshot, per-member command by configuration [ev:clawteam-probe-log#F16]. Verdict: clean on this host.

**5.3 PoC C — nested TeamRun.** Outer `ops` run; CodeMod Member runs `ats nest development --task "eliminate the OOM" --wait`. Core checks `nesting {allowed, max_depth}` and `depth < max`, creates inner run `run-c21d` with `parent {run_id: ops, member: codemod, task_id: t4}`, its own run dir and ClawTeam team named by run id, spawns the inner Lead first (so the creator is the Core, not CodeMod — trap 1 avoided [ev:clawteam-probe-log#F18]); outer task t4 → `delegated_to`. Inner Members get `ATS_RUN_ID=run-c21d`, fresh contexts (`--bare`, cloned profiles, new session keys), worktrees based on the outer task's branch. Core waits on inner terminal status (task list + registry liveness, not the inbox-draining `task wait` default). Isolation: ClawTeam enforces no inter-team boundary [ev:clawteam-probe-log#F19]; the Core records `independence.achieved: advisory` unless a separate `CLAWTEAM_DATA_DIR` per run is used (then `mechanical` for messages/tasks). New: nesting contract. Reused: CT team-as-namespace, snapshot [ev:clawteam-model#F22]. Verdict: clean; PoC C pass criteria (isolation, result, archive, no leak) map to 5.4.

**5.4 Nested result return + archive.** The inner Lead ends with `ats result --status completed --summary … --deliverables diff.patch,test-report.md --risks …` → Core writes RunResult into inner `run.json`, copies it into the outer task (`clawteam task update ops t4 --metadata` — untested with real agents, probe open question 3 [ev:clawteam-probe-log#F20]; fallback `inbox send ops codemod` notification, which is verified to deliver cross-team [ev:clawteam-probe-log#F19]), snapshots the inner team (`team snapshot`, survives cleanup [ev:clawteam-model#F28]), stops inner processes from `spawn_registry.json` pids (CT's `cleanup` does not [ev:clawteam-probe-log#F20]), then `team cleanup`. Outer archive gets `nested_runs[] {run_id, archive_ref}`. Failure: inner Lead dead with tasks pending → inner `aborted`, outer t4 `failed` + message. Leak check: definitions dir hash unchanged; inner ephemeral definitions stay in the inner archive. New: RunResult contract, process-stop, archive linking. Verdict: clean with one unverified mechanism (task metadata).

**5.5 Ensemble + synthesis.** As 5.1 Run 3, generalised: `ensemble {legs: [claude-code, codex], min_legs: 2, synthesis_harness: policy}` on any Member/task; each leg a HarnessInvocation with `ensemble_id`, own workspace, isolation knobs from its profile (`--bare`, `--ephemeral`, fresh Hermes profile) [ev:harness-cli-capabilities-a#F19][ev:harness-cli-capabilities-b#F24]; synthesis is a recorded third invocation. On the ClawTeam substrate the legs are simply N Members with distinct commands (probe-verified fan-out [ev:clawteam-probe-log#F16]); attribution comes from the Core's records, not CT's self-reported cost [ev:clawteam-model#F28]. New: Ensemble record, bundle identity, structured verdict. Verdict: clean.

**5.6 Evolution overlays + proposals.** After runs A and C, `ats evolve propose --runs run-A run-C`: the Core extracts findings/corrections/harness outcomes from archives, runs an `evolution-critic` Assistant through the broker with a proposal JSON schema, applies the project-independence filter (paths, branch names, session ids, topics, secrets [model:assistant-domain-model#4]), dedupes and caps volume, writes `proposals/<id>.yaml` pending. `ats evolve review` shows the diff; accept → entry appended to the Reviewed Evolution Overlay with `from_proposal`, `runs`, `approved {by, at, applied_hash}`; the resolver's next merge (Base → Evolution → User) changes the effective definition hash, which every later invocation records. Never applied automatically; `purpose/persona` edits rejected by the per-field policy [model:assistant-domain-model#9]. New: all four data-level objects. Reused: none needed (ClawTeam's plan round-trip is an option, not a dependency [ev:clawteam-model#F17]). Verdict: clean; heuristics-only filter is the known weak spot.

**5.7 Long-running operational run with deterministic backends.** `TeamRun.mode: operational` with `watchers[] {kind, config, schedule|event, trigger_rules, on_trigger}`; watchers are deterministic Backends with a BackendProfile and invocation records (no model/cost) [model:harness-broker-model#9]. A supervisor (`ats run supervise`) or an OS scheduler entry (systemd timer / launchd / schtasks) calls `ats run tick <run>`; on a fired rule the broker invokes Run & Monitor fresh (`--bare`, new session key) with a deterministic RunStateSummary; the decision log records trigger → invocation → decision → action. Where the owner already runs the OpenClaw gateway, `openclaw cron add --command` / `--message` is a pluggable scheduler [ev:openclaw-native-and-telegram-verification#F9]; never a prerequisite [fitgap:MS-01]. ClawTeam's resident-worker model is not used for this mode [ev:clawteam-model#F15]. New: watcher registry, tick evaluator, summary, decision log (S–M). Verdict: clean by design, most new code of the eight; post-PoC.

**5.8 Ephemeral hidden member audit.** Archive roster: `{name, origin: ephemeral, visibility: hidden, created_by, policy_decision, definition_ref (full rendered text), invocation: inv-05}`; invocation record: `argv_redacted`, `cwd`, `env_names`, `bundle_hash`, `stdout` path (the launcher tees — CT alone discards output and writes `exit_code: null` [ev:clawteam-spawn-platform#F21][ev:clawteam-probe-log#F14]), harness session id, usage. Reconstruction test: from the archive alone rebuild the exact bundle and command. User view omits hidden unless `--all`. Verdict: clean.

## 6. Cross-platform story (Ubuntu / macOS / Windows, tmux-free)

No tmux anywhere: the `direct` substrate is the Core's own `subprocess` (argv lists, `shell=False`); the ClawTeam substrate forces `backend=subprocess` (probe-verified here [ev:clawteam-probe-log#F12]) and never uses `launch`. Prompts and definitions travel by file wherever the harness allows (`--append-system-prompt-file`, `--message-file`, `--prompt-file`, `AGENTS.md`/`SOUL.md` in prepared dirs) to avoid cmd.exe truncation of multi-line `-p` [ev:clawteam-spawn-platform#F20]. Output and exit codes are the launcher's, so CT's Windows branch having no keepalive and no exit-code env does not matter [ev:clawteam-spawn-platform#F10]. On Windows the ClawTeam substrate must be configured `skip_permissions=false` (the `os.getuid()` crash) [ev:clawteam-spawn-platform#F20]; permissions flags are rendered by the Core's adapters instead. Vendored `platform_compat.py` covers locks and `pid_alive` [ev:clawteam-openclaw-fork-delta#F19]. Harness availability and host OS are recorded per invocation as independent dimensions (XC-02). macOS = the POSIX path (ClawTeam CI covers it). Honest gap: no candidate has Windows CI and no Windows/macOS probe exists; the PoC plan needs one headless invocation per harness and one CT `spawn subprocess` on each OS before TE-08 moves from documented to verified [fitgap:TE-08].

- Scope creep (ATM R5: design outran 666 product lines): PoC A first, with only definitions + two adapters + broker; run layer only after Run 3 passes.
- ATM schema text unusable until licensed; ideas only.

## 8. Where my bias breaks

1. **Size.** The Core is ~1.5–2× O2's new code; the substrate interface and the `direct` backend (~1.5–2k) are dead weight if the owner only ever runs ClawTeam-backed teams.
2. **"Multiple backends" is thinner today than the slogan.** Claude Code native teams are experimental, interactive-only, Claude-only, non-nested [ev:claude-agent-teams-hermes-openbot#F2][ev:claude-agent-teams-hermes-openbot#F7][ev:claude-agent-teams-hermes-openbot#F8]; Hermes kanban is Hermes-only [ev:claude-agent-teams-hermes-openbot#F25]; OpenClaw needs the gateway and the absent acpx plugin for sub-agent/ACP paths [ev:openclaw-native-and-telegram-verification#F16]. Realistically the backends are ClawTeam, direct CLI, and Claude subagents *inside* one Claude Member; the second coordination substrate is a promise.
3. **For any team run the Core still depends on ClawTeam** (or Hermes kanban); "independent" means independent of CT's formats, not its existence. If CT bit-rots (dead upstream, Python ≥3.10, `mcp<2` pin), the run layer needs a new substrate adapter sooner than I would like.
4. **"Profiles as data" is partly aspiration.** Injection recipes and output parsers are code per harness; five adapters are the same drift burden O2/O3 would carry.
5. **Time-to-PoC** favours O2 (and even O1 for a demo); my path is slower by a week or two.
6. **ATM risk R5** applies to me most: nine components is a design, not a product; only PoC A justifies the next component.
