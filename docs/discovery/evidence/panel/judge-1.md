# Judge 1 — requirements & evidence lens

## 1 Method

All three proposals were delivered (A = O2 "`ats` over the ClawTeam CLI"; B = O7 "independent Core with two seams, ClawTeam as one substrate"; C = O2+O3 "library over ClawTeam Python seams, upstream PRs filed"). I scored each proposal as the architecture it actually proposes, not the option label, on R1–R10 (1–5). ## 3 Per-proposal critique

### Proposal A — ClawTeam maximalist (answer: O2)

**Strengths.** The tightest bias-correction in the set: the author's own O1 bias is dismantled with probe facts (system prompt dropped for 8/10 CLIs [ev:clawteam-spawn-platform#F1][ev:clawteam-spawn-platform#F6]; Hermes `-p` invalid [ev:clawteam-spawn-platform#F2]; DEVNULL and `exit_code: null` [ev:clawteam-probe-log#F12][ev:clawteam-probe-log#F14]; no hidden flag [ev:clawteam-model#F1]; no parent link and cleanup leaves processes [ev:clawteam-probe-log#F18][ev:clawteam-probe-log#F20]). The compiler-not-`launch` decision is evidence-driven (`launch` swallows errors, one profile for all, no DAG edges [ev:clawteam-probe-log#F15][ev:clawteam-probe-log#F23][ev:clawteam-spawn-platform#F12]). The Hermes assessment is right: strong Harness (profiles, `-z --usage-file`, distributions), weak team backend (Hermes-only, un-nestable) [ev:claude-agent-teams-hermes-openbot#F22][ev:claude-agent-teams-hermes-openbot#F25]. The walkthroughs use the correct ClawTeam composition for nesting (`spawn-team` as self, `task wait --agent`, cross-team `inbox send`, snapshot before cleanup, SIGTERM registry pids) [ev:clawteam-model#F22][ev:clawteam-probe-log#F19].

**Factual errors / overstatements.**
1. "O2 size ≈3–4k LOC" and "absolute minimum ≈3k" contradict A's own component table, which sums to ≈4.35k before tests. Not material to ranking, but the smallest-layer claim should be numerically consistent.
2. A implies `--no-keepalive` makes PoC A legs one-shot and quiet; ClawTeam's wrapper still runs `lifecycle on-exit` after every exit (`keepalive.py:64-69`), which resets any `in_progress` task of that Member and messages the ClawTeam leader "exited unexpectedly" even on exit 0 [ev:clawteam-probe-log#F14]. For ensemble legs and operational triggers spawned through `clawteam spawn`, this is per-exit noise the Lead must learn to ignore; A does not mention it.
3. O4 R4 says PoC A/B/C "forbid" OpenClaw/Telegram; the register says "not required unless the analysis proves necessity" (product-intent §4). Wording, not substance.
4. The O7 R3 cite for "file prompts are the cleanest Windows path" is [ev:harness-cli-capabilities-a#F14] (platform support), which does not discuss file delivery; the supporting facts are [ev:harness-cli-capabilities-a#F2] (`--append-system-prompt-file`) and [ev:clawteam-spawn-platform#F20] (cmd.exe truncation).

**Coverage gaps.** (a) TC-05: the gate lives in `ats member add`, but the Lead holds ClawTeam's Skill, whose reference documents `clawteam spawn`; nothing in A stops a Lead from spawning around the gate (ClawTeam has no pre-spawn hook on the CLI path [ev:clawteam-spawn-platform#F16]). A's §9 omits this. (b) TE-05: §5 records "no isolation (any identity sends/waits on any team)" [ev:clawteam-probe-log#F19] but §9 does not list TE-05 as caveated; PoC C's "isolated inner task/message space" is met only as namespace isolation. (c) A's R4 self-score of 5 ("cleanly") is not supported by A's own "where convention broke" paragraphs — roster projection, process stop, exit-code capture are hacks around substrate holes, acceptable hacks, but hacks.

## 4 Reuse-ladder and cross-platform check

**Ladder discipline (XC-03).** The reuse analysis fixes the rungs: rung 1 for TE-01/02/03/06 mechanics on ClawTeam, rung 2 for injection rendering, nesting composition and output capture, rung 6 only for the ≈23 data objects, and "rung 3 is never the only path" [reuse:§2 "Reading across"]. Against that: **A** is exactly at those rungs (CLI wrapper + objects; optional rung-4 `platform_compat`). **B** is at the same rungs plus a seam and a `direct` spawn; the direct spawn is needed by every option for solo runs (PoC A has no team), so the seam is the only genuine extra — small, but it is abstraction ahead of a second team substrate that the evidence says does not exist (Claude Code teams, Hermes kanban, OpenClaw sessions all fail TE-03 or TE-05 [fitgap:TE-03][ev:claude-agent-teams-hermes-openbot#F7][ev:claude-agent-teams-hermes-openbot#F25][ev:openclaw-native-and-telegram-verification#F21]). **C** sits at rung 2 through library seams (no lower than A's CLI rung and riskier by the reuse doc's own risk note) and at rung 3 for PRs whose rung-2 shadows must exist anyway — C concedes this. None of the three proposes rung 5 or rung 6 for team execution; all three correctly reject O8 by [fitgap:TE-01] ("not genuinely new — reachable at rung 1–3").

**Cross-platform honesty (TE-08, XC-02).** All three state that no candidate has Windows CI and nothing was probed off this host [ev:clawteam-spawn-platform#F20][ev:clawteam-openclaw-fork-delta#F25] — consistent with the fit-gap (TE-08 best `C!` for CTF, `S?~` for the harnesses). Specifics: A's `skip_permissions=false` mitigation is valid (`adapters.py:49-53`); A's wrapper capturing exit codes compensates for CT's Windows branch having none [ev:clawteam-spawn-platform#F10]. B's direct substrate is the best Windows path on paper but its team path has the `--task`/cmd.exe inconsistency. C avoids `shell=True` and DEVNULL at the source, the mechanically cleanest path, but only if ClawTeam's Python package behaves on Windows and only with the registry hack. No proposal addresses macOS beyond "POSIX + CI" [ev:clawteam-spawn-platform#F20], which is adequate. Verdict: all three are honest that TE-08 is *documented, not verified*; the owner must decide whether a probe precedes acceptance (§7).

**Glossary compliance.** Spot-checked: all three use "agent/leader/worker" only for ClawTeam's concepts and "Member/Lead/TeamRun" otherwise; no ATM demoted concept re-enters (no reconciliation, no persistent runtime identity, no A2A router, no topic topology) [model:legacy-atm-disposition#2].

## 5 Endorsement and required amendments

**Endorsed: a named composition — "B's ownership model and two seams, built at A's scope, with C's caveats and C's PRs as optional accelerators."** Concretely:

- Ownership (from B): definitions, overlays, Proposals, HarnessProfiles/policy, invocation ledger, run manifest/roster/nesting contract and archive are substrate-neutral data owned by the layer; ClawTeam is reached through one CoordinationSubstrate adapter over its **CLI** (not library seams); harnesses through HarnessAdapters = profile data + four functions [model:harness-broker-model#10].
- Scope (from A): ClawTeam is the **only** team substrate built; the `direct` path exists only for solo runs and ensemble legs (PoC A); no Claude-Code-teams, OpenClaw-session or Hermes-kanban team backends are built (evidence: none can host a mixed-harness nested TeamRun [fitgap:TE-03][fitgap:TE-05]); the compiler drives `spawn` per Member, never `launch` [ev:clawteam-probe-log#F15][ev:clawteam-probe-log#F23].
- Honesty (from C): adopt C's §9 caveat list verbatim into the M-row coverage statement; file C8's small PRs (getuid guard, `mcp<2`, logs + exit code, `created_by`, `hidden`, cleanup stops processes, Hermes/Grok branches, `launch` errors, `blocked_by` validation) as intent, and plan as if none merges [ev:clawteam-spawn-platform#F24].

Why this and not A alone: A is the smallest honest answer, but the two things B adds cost little and are justified by evidence — the `direct` spawn is required for PoC A anyway, and the substrate seam is cheap insurance against a dormant upstream whose packaging already broke once (`mcp` 2.0 [ev:clawteam-probe-log#F1]). Why not B alone: B's title and size over-claim "multiple backends" the evidence does not support today, and B's R1/R7 costs come from scope the register does not demand (five adapters, a full second substrate) — cut to A's scope. Why not C: the library-seam coupling and the PR dependency are the two weakest-evidenced bets on the table (Alpha seams, no `__all__`, no commits since May; and the custom-backend liveness premise is false).

**Amendments I require before this becomes `architecture-options.md`'s answer:**

1. **State the substrate truth in one sentence:** "ClawTeam (CLI, pinned 0119833/0.3.0, `mcp<2`) is the sole team substrate; `direct` is a solo/ensemble launcher; 'independent' means format-independent, not substrate-free." Remove "multiple backends" from the title.
2. **No `--task` through `clawteam spawn` on any OS.** The bundle (persona, principles, coordination section) is delivered by the layer's wrapper from a file; ClawTeam appends nothing when no prompt is given (`adapters.py:131-140`). This removes the cmd.exe truncation path and makes B's §6 true. Probe it on day one.
3. **Declare the on-exit behaviour.** Every `clawteam spawn subprocess` exit, clean or not, runs `lifecycle on-exit` (`keepalive.py:64-69`): task reset + "exited unexpectedly" to the ClawTeam leader [ev:clawteam-probe-log#F14]. For one-shot Members (ensemble legs, operational triggers) either spawn via `direct` and register nothing in ClawTeam, or document the noise in the Lead Skill. Decide; do not leave it implicit.
4. **TC-05 is "gate + convention" until enforced.** Record the gate decision in the roster; mitigate bypass with the Lead Skill text and C's `CLAWTEAM_BIN` shim that refuses `spawn` inside a run; label TC-05 accordingly in R10. Mechanical enforcement needs either an upstream hook PR or ownership of the spawn path (C8 / O6 fallback).
5. **TE-05 isolation level is recorded, not assumed.** Per nested run write `independence.achieved: namespace | data-dir` (per-run `CLAWTEAM_DATA_DIR`, bypassable by `--data-dir`); probe whether per-run data dirs break the creating Member's `task wait`/inbox discovery [model:team-execution-model#13 Q5].
6. **Liveness stays on ClawTeam's own backend names.** Anything registered in `spawn_registry.json` must carry `backend: subprocess` + pid, or the layer must track liveness itself; never rely on a custom backend name being understood by `is_agent_alive`/`stop_agent` (`registry.py:55-79,121-168`).
7. **Day-one probes, listed as PoC preconditions:** (a) `codex exec -c developer_instructions=…` honoured on 0.148.0 and `codex` positional prompt without a TTY [ev:harness-cli-capabilities-a#F2][ev:clawteam-spawn-platform §5 q.1]; (b) `claude -p --bare --append-system-prompt-file` under the wrapper with output tee [ev:harness-cli-capabilities-a#F17][ev:harness-cli-capabilities-a#F19]; (c) Hermes `--source tool` hiding and memory writes on 0.20.4 if a Hermes Member is in PoC B [ev:harness-cli-capabilities-b §5]; (d) one Windows and one macOS smoke of the wrapper + one `clawteam spawn subprocess` [fitgap:TE-08].
8. **Size by slice, not by total.** Commit only to the PoC-A slice first (definition schema + validator, two adapters, broker resolve/record, wrapper, ledger; ≈2–3k) and gate the run layer on PoC A passing; reconcile the 4k/8k/11k estimates against that slice, not against each other (ATM R5 [model:legacy-atm-disposition#4]).

## 6 Dissent

A reasonable colleague would still argue:

- **A alone, no seam.** The seam is YAGNI: the evidence shows no second team substrate, and the `direct` launcher is ≈300 LOC inside A's wrapper anyway. Every abstraction the PoCs do not exercise is ATM's design-outruns-execution risk again [ev:atm-salvage#F27].
- **C's library route is safer than it looks.** A dormant upstream does not drift; pinned to 0119833, `TeamManager`/`FileTaskStore`/`MailboxManager` are stable by inactivity, and importing them avoids three shell-level hacks (cmd.exe wrapper, DEVNULL, `-p` append) at the source. The liveness problem is one registry field. If the implementation language is Python, this is the cleanest Windows path of the three.
- **O1 first as a zero-code demo.** A TOML template with `claude` and `codex` members plus a `tee` wrapper would show within hours whether ClawTeam's subprocess path carries a Codex Member at all (open question 1 of [ev:clawteam-spawn-platform]); building any layer before that answer is premature.
- **Hermes as the all-Hermes substrate.** For a single-harness operational team (LO rows), Hermes profiles + kanban dispatch + `--usage-file` already give fresh-per-task workers, durable runs and cost records [ev:harness-cli-capabilities-b#F19][ev:claude-agent-teams-hermes-openbot#F25]; ClawTeam's resident-worker model is the inverse of LO [ev:clawteam-model#F15]. If the owner's first real use is training operations, the cheapest substrate may not be ClawTeam.
- **B's broader adapter set is not gold-plating** if the owner truly runs five harnesses today (recon: all five installed); profiles-as-data for Grok/OpenClaw cost mostly data, and a broker tested on two harnesses is a weaker PoC A than the brief's "same Assistant on both" implies.
