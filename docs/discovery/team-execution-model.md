# Team execution model

## 1. Purpose & scope

This document models how a persistent **TeamTemplate** becomes a fresh **TeamRun**, what a run owns while it lives, what it leaves behind, and where today's substrates stop. It owns three pressure tests (temporary hidden member, nested TeamRun, long-running operational run). Requirements are cited by ID from `product-intent.md` §3; Assistant content and overlays belong to `assistant-domain-model.md`; harness selection, definition injection and invocation records to `harness-broker-model.md` — where a run needs those it names the contract it consumes. Fit cells come from `existing-systems-fit-gap.md` and are not re-classified here (where this document quotes the W3 owner re-score of TE-05, §14 says so). A TeamTemplate is data; a TeamRun is a directory of temporary state plus an archive; Members are slots; AssistantInstances are what the HarnessBroker materialises into HarnessInvocations.

## 2. TeamTemplate content model (TC-01..TC-06)

Illustrative, not a schema:

```yaml
team_template:
  id: development                    # stable name; versioned by content hash
  members:
    - {name: lead, assistant: assistants/implementation-planner,      # TC-01: by reference
       relationships: {coordinates: [implementer, reviewer]}, visibility: visible}
    - {name: implementer, assistant: assistants/implementer}
    - {name: reviewer, assistant: assistants/code-reviewer, relationships: {reviews: [implementer]}}
  lead: lead                                          # TC-02
  handoff: {required_fields: [task_id, summary, deliverables, risks, done_when], acks: [ACK, DONE, BLOCKED]}
  independence:                                       # TC-03 — the template only *declares*; `achieved` is a run fact (§3.3, §6 item 4)
    - {between: [reviewer, implementer], declared: advisory,          # advisory | mechanical — declaring mechanical fails closed on every current substrate; PoC B declares advisory
       means: [separate_invocation, no_shared_workspace, no_message_edge, blinded_inputs]}
  visibility_defaults: {persistent_members: visible, dynamic_members: hidden}   # TC-04
  dynamic_members:                                    # TC-05
    {may_create: [lead], max_count: 3, allowed_harnesses: [claude-code, codex, hermes],
     nesting: {allowed: true, max_depth: 1}}
  preferences:                                        # TC-06: stable, project-independent
    harness_preferences: {reviewer: [codex, claude-code]}   # data only; precedence in harness-broker-model
    run_defaults: {fresh_instances: true, archive: always, worktree_per_member: true}
  workflow_skeleton:                                  # optional; placeholders only
    - {subject: "Plan {goal}", owner: lead}
    - {subject: "Implement plan", owner: implementer, blocked_by: [0]}
```

**What each block means and where it comes from.**

- *members / lead / relationships*: composition by reference (TC-01) exists in no runnable substrate: ClawTeam's `AgentDef{name,type,task,command}` inlines the persona as `task` prose [ev:clawteam-model#F13][ev:clawteam-probe-log#F4]; OpenClaw has no template object [ev:openclaw-native-and-telegram-verification#F21]; dsh-agent-team-gui's `SquadRecord → AgentRecord` is the nearest shape but DSH-bound [ev:dsh-agent-teams-and-gui#F18]. Lead-as-declared-slot follows ClawTeam `TemplateDef.leader` [ev:clawteam-model#F13] / `TeamConfig.leadAgentId` [ev:clawteam-model#F1] and DG `leaderAgentId` [ev:dsh-agent-teams-and-gui#F18]. Relationships are directed edges (ATM `topology.allow` precedent [ev:atm-salvage#F12]).
- *handoff*: conventions are template data consumed by Lead and Members; the vocabulary borrows the openclaw-kit HANDOFF/ACK/DONE/BLOCKED fields [ev:openclaw-native-and-telegram-verification#F5] and DG's bounded `SquadMemberHandoff{summary, deliverables, risks, changedFiles}` [ev:dsh-agent-teams-and-gui#F24]. Transport is the substrate's (ClawTeam inbox, Hermes kanban comments, dsh mailbox).
- *independence (TC-03)*: "independent" is operational: (i) **separate invocation** — the reviewer is its own AssistantInstance/HarnessInvocation, never a fork of the writer's session (DG `contextMode=spawn` vs `fork` [ev:dsh-agent-teams-and-gui#F25]; Hermes `delegate_task` children are "a fresh conversation" [ev:claude-agent-teams-hermes-openbot#F22]); (ii) **no shared workspace** — distinct worktree/cwd (ClawTeam `workspaces/{team}/{agent}` [ev:clawteam-probe-log#F22]); (iii) **no message edge** — the run layer refuses to deliver writer↔reviewer messages; (iv) **blinded inputs** — the reviewer sees the artifact under review, not the writer's rationale or transcript. `advisory` = (i)–(iv) stated in prompts; `mechanical` = the run layer enforces (i)–(iii) and fails closed when the substrate cannot (ATM ADR 0026 "must not silently fall back" [ev:atm-salvage#F14]). No substrate enforces (iii) today: ClawTeam delivers to any recipient string [ev:clawteam-probe-log#F9][ev:clawteam-probe-log#F19]; OpenClaw's `agentToAgent.allow` is global membership [ev:atm-salvage#F5]. Two fields, not one: the template **declares** `independence.declared: advisory | mechanical`; every run (and every nested run) **records** `independence.achieved: namespace | data-dir | mechanical` — the vocabulary originates with the panel judges ([panel:judge-1.md#5] item 5 `namespace | data-dir`; [panel:judge-2.md#5] item 5 `advisory | mechanical`) and was fixed by the owner tiebreak assumption (e) [panel:owner-tiebreak.md]; this document adopts it. Consequence stated plainly: declaring `mechanical` fails closed on every current substrate today (none enforces (iii)); PoC B therefore declares `advisory` (`minimal-poc-plan.md` §4) and PoC C records `achieved` honestly (`minimal-poc-plan.md` §5).
- *visibility_defaults / dynamic_members (TC-04, TC-05)*: who / how many / which harnesses / nesting depth. Precedents: OpenClaw `subagents{maxSpawnDepth, maxChildrenPerAgent, allowAgents, requireAgentId}` [ev:openclaw-native-and-telegram-verification#F21], dsh `maxMembers`/`memberMaxDepth` [ev:dsh-agent-teams-and-gui#F4], ATM `spawn{intraRole,maxDepth}` [ev:atm-salvage#F11]. Only OpenClaw's can name a harness, and only per persistent `agents.list` entry.
- *preferences (TC-06)*: team-level, project-independent; harness preferences are data whose precedence and resolution belong to `harness-broker-model.md`.
- *workflow_skeleton*: optional task shapes with placeholders — what ClawTeam templates already carry (`tasks[]` with `{goal}`) [ev:clawteam-model#F13]; a shape, never a project's task list.

**What a TeamTemplate must NOT contain** (AD-05/TC-06, enforceable by schema): repo/paths/branches, workspace dirs, a project's concrete tasks, harness session ids, Telegram topics or any Surface binding, runtime agent ids (ClawTeam `agentId`, OpenClaw `agents.list` id, a Hermes profile name used as identity), credentials or env values, run results, ephemeral member definitions. OpenClaw's reusable unit fails this by design (`agents.list[]` owns workspace/agentDir/sessions) [ev:harness-cli-capabilities-b#F10]; so does a Hermes profile (`sessions/`, `memories/`, `.env`) [ev:claude-agent-teams-hermes-openbot#F23].

## 3. TeamRun lifecycle (TE-01, TE-02, TE-07)

Three phases; every transition is an archive entry.

**3.1 Instantiate.** Inputs: `template_ref` (+hash), `project` (repo/path, branch, data paths, credential *references*), `task` (goal, acceptance), `harness_overrides` (user-level, per member), `options` (visibility overrides, resume opt-ins). Steps: (1) resolve each member's effective definition per `assistant-domain-model.md` §9 (merge order Base → Reviewed Evolution Overlay → User Overlay; hash recorded); (2) ask the HarnessBroker for a harness per member and record the binding; (3) allocate a run id and directory and write `run.json` with `status: started` — **before** the substrate team exists and before any process starts (the manifest is rewritten at every later transition, so an aborted run still leaves a terminal record — `legacy-atm-disposition.md` R4; `minimal-poc-plan.md` §4 step (1)); (4) materialise workspaces (per-member worktrees where the template says so); (5) create the substrate team and tasks from `workflow_skeleton`; (6) spawn AssistantInstances (Lead first) as HarnessInvocations. ClawTeam's `launch` does 4–6 for its own TOML [ev:clawteam-probe-log#F23] but hides spawn failures [ev:clawteam-probe-log#F15], applies one `--profile` to all agents [ev:clawteam-spawn-platform#F12] and has no task edges — so the run layer drives `spawn` per member rather than calling `launch`.

**3.2 Run.** Fresh instances by default (TE-02): each Member's AssistantInstance starts a new harness session (ClawTeam passes a new `--session-id` per spawn [ev:clawteam-spawn-platform#F19]; Claude `-p`, Codex `exec`, Hermes `chat -q` are fresh [ev:harness-cli-capabilities-a#F8][ev:harness-cli-capabilities-b#F19]); resume is an explicit per-member option (`spawn --resume` [ev:clawteam-spawn-platform#F19]; OpenClaw `--session-key` reuse [ev:atm-salvage#F4]). Temporary state lives only under the run directory: task graph, inboxes/events, spawn registry, workspace registry, session pointers, cost events, dynamic-member definitions, nested-run references, decision log. The Lead coordinates through the substrate DAG and messages (§8); dynamic members (§5) and nested runs (§6) are run-layer operations that call the substrate.

**3.3 Archive.** Kept: `run.json` manifest (template ref+hash, Assistant refs+hashes, overlays applied, project identifiers), **the full Member roster including hidden and ephemeral Members** (with their generated definitions), final task graph plus history, messages and events, HarnessInvocation records (by reference to the broker's ledger: harness, version, model, cost, outcome, transcript path), deliverables (paths/hashes/diff refs), nested-run references, a timeline of automated actions. Discarded: worktrees after merge/cleanup, temp env files, live process registries, the substrate's *mutable* team dir once snapshotted. Never persisted anywhere else: project facts into an Assistant or TeamTemplate (EV-04); transcripts are referenced, not copied into definitions. Evolution reads the archive to generate Proposals (EV-03); nothing else flows back. ClawTeam's `team snapshot` (config, tasks, events, sessions, costs, pending inboxes) survives `team cleanup` [ev:clawteam-model#F22] and is the archive's substrate half; its holes — DEVNULL output, `exit_code: null`, cleanup deletes and leaves processes — are probe-verified [ev:clawteam-probe-log#F12][ev:clawteam-probe-log#F14][ev:clawteam-probe-log#F20] and closed by the run layer capturing output and exit codes itself (§9).

Illustrative run record (not a schema):

```yaml
team_run:
  id: run-7f3a
  template: {ref: development, hash: sha256:…}
  parent: null                      # or {run_id, member, task_id} for a nested run
  depth: 0
  independence: {declared: advisory, achieved: namespace}   # declared = template (§2); achieved ∈ namespace | data-dir | mechanical, recorded per run (§6 item 4)
  project: {repo: /work/trainer, branch: fix/oom}
  task: "Fix the dataloader OOM seen in run42"
  members:
    - {name: lead, assistant: {ref: implementation-planner, hash: …}, origin: persistent,
       visibility: visible, harness: claude-code@2.1.239, invocation: inv-01}
    - {name: migsafe, assistant: {ref: run/ephemeral/migsafe.md, hash: …}, origin: ephemeral,
       visibility: hidden, created_by: lead, policy_decision: "allowed (1/3)", harness: codex@0.148.0, invocation: inv-05}
  substrate: {kind: clawteam, team: run-7f3a}
  tasks: [{id: t4, subject: "…", status: completed, owner: codemod, delegated_to: run-c21d}, …]
  nested_runs: [{run_id: run-c21d, created_by: codemod, outer_task: t4, status: completed,
                 result: {status: completed, summary: "…", deliverables: […], risks: […], archive_ref: …},   # RunResult copy, layer-owned (§6 item 3)
                 independence: {declared: advisory, achieved: namespace}, archive: …}]
  status: completed
  archive: {snapshot: snap-….json, invocations: [inv-01, …, inv-07]}
```

## 4. Mixed harnesses in one run (TE-03)

A Member is bound to one HarnessInvocation at a time; Members may differ in harness because binding happens per Member at instantiate (or at dynamic creation). The run layer hands the broker the resolved Assistant, receives command + cwd + env + a record of what was injected, and spawns through the substrate. On ClawTeam this is configuration: per-agent `command` in a template (alpha→noopA, beta→noopB) and `spawn --profile` are probe-verified [ev:clawteam-probe-log#F16][ev:clawteam-probe-log#F17], precedence CLI command > profile > `claude` [ev:clawteam-spawn-platform#F5]. Consequences: (a) ClawTeam's adapter chain knows nine CLIs plus a generic fallback (`is_*_command` for claude, codex, nanobot, gemini, kimi, qwen, opencode, openclaw, pi — ClawTeam/clawteam/spawn/adapters.py:156-224), adds a system prompt for claude/pi only and falls back to `-p <prompt>` — invalid for Hermes, which wants `chat -q` [ev:clawteam-spawn-platform#F1][ev:clawteam-spawn-platform#F2][ev:harness-cli-capabilities-b#F6]. An explicit positional command suppresses only the *implicit profile* [ev:clawteam-spawn-platform#F5]; `NativeCliAdapter.prepare_command` still runs on every `spawn` — for a recognised basename it appends `--session-id` and the bypass flag, for any command it appends `-p <prompt>` (or a positional prompt) whenever `--task` is given, and `os.getuid()` is evaluated whenever `skip_permissions` is true, the config default [ev:clawteam-spawn-platform#F1][ev:clawteam-spawn-platform#F10][ev:clawteam-probe-log#F12]. The mechanism is therefore: the run layer spawns `clawteam spawn subprocess --team <run> -n <member> -- <ats-wrap …>` with an **unrecognised wrapper basename**, passes **no `--task`** (adapters.py:131-140 then appends no prompt), writes `skip_permissions: false` into the layer-owned ClawTeam config (adapters.py:53 `os.getuid()` is never evaluated), and the wrapper delivers the injection bundle from a file and launches the harness with the fully rendered argv — ClawTeam is the coordination substrate, never the harness adapter; (b) a Hermes Member is `hermes chat --source tool -q … [-p <profile>]` (no JSON/usage output) or the one-shot `hermes -z … --usage-file` form when a cost record is required [ev:harness-cli-capabilities-b#F6][ev:harness-cli-capabilities-b#F7]; an OpenClaw Member is one-shot `openclaw agent --local --session-key … --message-file …` or the fork's resident `tui --session` form [ev:harness-cli-capabilities-b#F1][ev:clawteam-openclaw-fork-delta#F4]; a Claude Member `claude -p --append-system-prompt-file … --bare`; a Codex Member `codex exec -c developer_instructions=…` (observed, unverified) [ev:harness-cli-capabilities-a#F17]. Single-harness substrates (Claude Code teams, Hermes kanban, dsh) cannot host a mixed run (fit-gap TE-03 M) but can host one Member or an all-one-harness nested run.

## 5. Pressure test — temporary hidden member (TE-04, AD-07, TC-05, TE-07)

**Scenario.** A Dev TeamRun {Lead, Implementer, Reviewer} is mid-way; the Lead notices the change touches a DB migration and wants a one-off "migration-safety specialist" to vet it. The user should not see a fourth colleague appear in the roster; the archive must show it; nothing of it becomes a reusable package unless a human later promotes it.

**Walkthrough — ClawTeam today.** (1) The Lead runs `clawteam spawn subprocess <cmd…> --team <run> -n migsafe --agent-type migration-safety --task "<prompt>" [--skill x] [--repo …]`; the member is auto-registered in `config.json members[]` and spawned [ev:clawteam-probe-log#F18][ev:clawteam-model#F5]. (2) The Lead can pass `--task` text, an `--agent-type` string, a `--skill` (inlined into `--append-system-prompt` for claude/pi only), a command/profile, a workspace — no persona object; the worker prompt is Identity + Task + protocol [ev:clawteam-model#F15][ev:clawteam-spawn-platform#F6]. (3) Visibility: none — `TeamMember{name,user,agentId,agentType,joinedAt}` has no flag; `team status`/`board show` list every member [ev:clawteam-model#F1][ev:clawteam-probe-log#F10]. (4) Gate: any process may spawn into any team; `request-join`/`approve-join` is Lead-gated but `spawn` bypasses it; no count cap [ev:clawteam-model#F5][ev:clawteam-model#F12]. (5) Audit: `spawn_registry.json` records backend/pid/full argv including the prompt [ev:clawteam-probe-log#F13]; sends are mirrored to `events/` [ev:clawteam-probe-log#F9]; but stdout/stderr go to DEVNULL and the exit journal records `exit_code: null` [ev:clawteam-probe-log#F12][ev:clawteam-probe-log#F14]; `--replace` stops a same-name member; there is no `remove-member` CLI (fit-gap TE-04 rationale).

**Walkthrough — others.** Claude Code: the Lead (interactive, teams enabled) spawns a background subagent (`background: true`; `--agents '<json>'` verified) whose transcript lands in `…/subagents/agent-{id}.jsonl`; not a teammate, so absent from the roster; teammates cannot background subagents; new subagent *definitions* mid-run need files under `.claude/agents/` (inferred from the scope order — `--agents` CLI JSON is "session only"; unprobed) [ev:claude-agent-teams-hermes-openbot#F11][ev:claude-agent-teams-hermes-openbot#F7][ev:harness-cli-capabilities-a#F7]. dsh-agent-teams: `captain`-only `agent_teams_add_member(name, role, provider, model)`, `maxMembers`, depth cap; no hidden flag, the activity panel shows all [ev:dsh-agent-teams-and-gui#F4][ev:dsh-agent-teams-and-gui#F12]. OpenClaw: `sessions_spawn` yields an isolated, auto-archived `agent:<id>:subagent:<uuid>` session, gated by `subagents.*`, audited by `openclaw tasks/audit` — but the child receives only AGENTS.md + TOOLS.md, no SOUL.md [ev:openclaw-native-and-telegram-verification#F21][ev:openclaw-native-and-telegram-verification#F14]. Hermes: `delegate_task` spawns fresh-context children (which cannot target another profile or harness); `--source tool` hides sessions from user lists [ev:claude-agent-teams-hermes-openbot#F22][ev:harness-cli-capabilities-b#F6].

**Breakpoints.** B1 No Member-level `visibility` attribute in any team substrate; hiding is implicit (OpenClaw sub-agent vs bound agent, Claude background subagent, Hermes source tag) and entangled with *capability* (OpenClaw sub-agents lose session tools; Claude background subagents cannot be teammates). B2 The ephemeral unit is task text, not an Assistant: no substrate lets the Lead hand over persona + principles + Skill/Capability requirements + harness preference for a temporary Member (OpenClaw drops SOUL.md; ClawTeam has no slot) — AD-07 requires an auditable *definition*. B3 No policy gate at the spawn point naming who/how-many/which-harness (ClawTeam: none — any process may spawn into any team [ev:clawteam-model#F5], `BeforeWorkerSpawn` never fires on the CLI spawn path [ev:clawteam-spawn-platform#F16], and every spawned Member receives `CLAWTEAM_BIN` plus a `## Coordination Protocol` naming the exact `clawteam` verbs [ev:clawteam-probe-log#F12], so a Lead with shell access can call `clawteam spawn --team <run>` itself and bypass any gate the run layer puts in front of its own spawn call; OpenClaw: per persistent agent; Claude/Hermes/dsh: cannot name a harness). B4 Audit fidelity: ClawTeam discards output and exit code; Claude Code deletes the team config at session end [ev:claude-agent-teams-hermes-openbot#F4]. B5 User-facing roster and archive roster are one list (ClawTeam, dsh), so "hidden from the UI but auditable" is inexpressible.

**Minimal addition.** The run layer owns the roster; substrate membership is a projection of it. Concretely: (1) `Member{visibility, origin: persistent|ephemeral, definition_ref, created_by, policy_decision}` — origin, creator and definition reference live on this roster entry, never inside the Ephemeral Assistant definition itself (`assistant-domain-model.md` §8 keeps the definition run-fact-free); (2) an **Ephemeral Assistant** is written by the Lead as a definition file *inside the run directory* (the persistent Assistant content model minus persistence — `assistant-domain-model.md` owns its shape) and is what gets injected, not a bare task string; (3) the Lead requests creation through the run layer, which evaluates `dynamic_members` (requester, count, depth, allowed harnesses) **before** calling the substrate spawn. Enforcement level, stated honestly: on ClawTeam today the achievable level is **gate + convention + run-scoped `CLAWTEAM_BIN`/PATH shim that refuses raw `spawn` inside a run + post-hoc roster/registry reconciliation** (`spawn_registry.json` checked against the roster after the run); the Lead CAN bypass it by calling `clawteam spawn` directly — there is no pre-spawn hook on the CLI path [ev:clawteam-spawn-platform#F16] — so B3 is narrowed, not closed; mechanical enforcement needs the upstream hook PR or owning the spawn path (`architecture-options.md` §3, §7 Q3), and PoC B records the level reached (`minimal-poc-plan.md` §4); (4) two projections of one roster: user-facing (filters `hidden` unless the user opts in) and archive (everything, including output captured by the run layer's wrapper); (5) promotion to a reusable package is a separate human-reviewed action (EV-03), never automatic. On ClawTeam this is `spawn` + a sidecar member record + an output tee; a `visibility` field on `TeamMember` would be a bounded upstream change (fit-gap TC-04 Xs!) [ev:clawteam-model#F1].

## 6. Pressure test — nested TeamRun (TE-05, TE-07)

**Scenario.** Training Operations TeamRun `ops` {Run & Monitor, Evaluator, Code Modification Assistant}. Run & Monitor hands CodeMod task `t4` "eliminate the dataloader OOM". CodeMod judges it needs a development team, instantiates the `development` TeamTemplate as an inner TeamRun {Planner, Implementer, Reviewer, Tester}, waits, receives the result (diff + test report), reports to Run & Monitor; the inner run is archived; `ops` continues.

**Walkthrough — ClawTeam as it exists.** (1) CodeMod (env `CLAWTEAM_TEAM_NAME=ops, CLAWTEAM_AGENT_NAME=codemod`) runs `clawteam spawn … --team dev-c21d -n planner --task …`; `dev-c21d` is auto-created and **planner becomes its ClawTeam `leader`** (`CLAWTEAM_AGENT_LEADER=1`); CodeMod is not a member of it [ev:clawteam-probe-log#F18][ev:clawteam-model#F22]. (2) The child env is CodeMod's environment with the five identity keys overridden; `CLAWTEAM_USER/DATA_DIR/TRANSPORT/WORKSPACE_DIR` are inherited; nothing reads the caller's identity [ev:clawteam-model#F3][ev:clawteam-model#F22]. (3) No parent field: `TeamConfig{name, description, leadAgentId, createdAt, members, budgetCents}`; `team discover` lists `ops` and `dev-c21d` flat; grep parent/nested → 0 [ev:clawteam-probe-log#F6][ev:clawteam-model#F1]. (4) Avoiding trap 1: CodeMod first runs `team spawn-team dev-c21d -n codemod` (leader id from its own env), then spawns children; their `idle`, "All tasks completed" and `on-exit` notices then land in `teams/dev-c21d/inboxes/codemod`, which CodeMod must poll explicitly (`inbox receive dev-c21d --agent codemod`) [ev:clawteam-model#F22]. (5) Waiting: `task wait dev-c21d --agent codemod --timeout …` blocks until all inner tasks are `completed`; without `--agent` it drains the inner leader's inbox (trap 2); zero tasks → immediate `completed` [ev:clawteam-model#F8][ev:clawteam-probe-log#F7]. (6) Result return: by convention only — `inbox send ops codemod "<result>"` from an inner member is delivered (cross-team send works from anywhere) [ev:clawteam-probe-log#F19]; `clawteam task update` has **no `--metadata` verb** in 0.3.0@0119833 (options are `--status/--owner/--subject/--description/--priority/--add-blocks/--add-blocked-by/--force`, ClawTeam/clawteam/cli/commands.py:2184-2191), so the outer task can carry at most a `--description` pointer and the `TaskItem.metadata{}` field [ev:clawteam-model#F6] is unreachable from the CLI — probe open question 3 ("`inbox send` vs `task update --metadata`") is moot as posed. (7) Isolation: none — any identity may send to, receive from and wait on any team; stray inboxes appear on demand [ev:clawteam-probe-log#F9][ev:clawteam-probe-log#F19]. (8) Failure: an inner ClawTeam worker's `on-exit` resets inner tasks and messages the inner leader; nothing is written under `ops` [ev:clawteam-model#F22]. (9) Archive: `team snapshot dev-c21d` bundles config/tasks/events/sessions/costs/inboxes and survives cleanup [ev:clawteam-model#F22][ev:clawteam-model#F28]. (10) Cleanup: `team cleanup dev-c21d` rmtree's data, does not stop processes, leaves `harness/dev-c21d`; an orphaned worker recreates dirs; `TeamShutdown` is never emitted [ev:clawteam-probe-log#F20][ev:clawteam-model#F22]. (11) Worktrees: an inner member's branch is based on the caller's current branch when spawned from the parent's worktree (step 6 of [ev:clawteam-model#F22], inferred).

**Walkthrough — others.** dsh-agent-teams denies members `agent_teams_create` and allows one active team per `captain`; `memberMaxDepth` permits only a star of plain DSH subagents [ev:dsh-agent-teams-and-gui#F3][ev:dsh-agent-teams-and-gui#F14]; dsh-agent-team-gui blocks nested dispatch for delegated sessions by lineage check and tool denial [ev:dsh-agent-teams-and-gui#F26]. Claude Code: "No nested teams: teammates cannot spawn their own teammates"; subagents nest ≤3 and return tool results with one transcript per subagent — a tree, not a coordination space [ev:claude-agent-teams-hermes-openbot#F7][ev:claude-agent-teams-hermes-openbot#F11]. Hermes: `delegate_task` is `MAX_DEPTH = 1` flat by default, opt-in `max_spawn_depth` + `role="orchestrator"`, per-task `output_schema` (a result contract), live logs; kanban `--parent ID` links tasks but "cannot spawn a board within a board" [ev:claude-agent-teams-hermes-openbot#F22][ev:claude-agent-teams-hermes-openbot#F25]. OpenClaw: `maxSpawnDepth` 1–5, depth-2 leaves have no session tools, children own a new context, announce back, auto-archive after `archiveAfterMinutes`, a lineage projection links the parent; no team/task object [ev:openclaw-native-and-telegram-verification#F21][ev:openclaw-native-and-telegram-verification#F22].

**Breakpoints.** N1 *Parent linkage*: no substrate stores "created by Member X of run Y for task Z" (ClawTeam none; OpenClaw/Hermes/Claude link sessions, not runs). N2 *Isolation*: ClawTeam is namespace-only; OpenClaw/dsh trees isolate context but offer no inner task DAG or mailbox. N3 *Result-return contract*: absent except Hermes' per-task `output_schema` and Claude tool results — both single-harness, neither a run-level object. N4 *Archive nesting*: ClawTeam snapshots per team with no link; OpenClaw auto-archives sessions; no outer archive references an inner one. N5 *Failure propagation*: the death of an inner Member's process (its HarnessInvocation) is invisible to the outer Member unless it polls; a team has no terminal status. N6 *Recursion limits*: ClawTeam none; OpenClaw/Claude/Hermes numeric depth on sessions, not runs; dsh forbids. N7 *Leak prevention*: ClawTeam writes nothing to definitions but shares `DATA_DIR` and bases inner worktrees on the parent's branch; OpenClaw/Hermes children inherit agent/profile memory unless a fresh agent/profile is used [ev:harness-cli-capabilities-b#F10][ev:harness-cli-capabilities-b#F19]. N8 The leader and `task wait` inbox traps in ClawTeam.

**Minimal addition — a nesting contract** (a model, not code):

1. **Creation through the run layer.** A Member asks the run layer to instantiate template `T` for task `t`; the run layer checks `dynamic_members.nesting` and `depth < max_depth`, then creates an inner TeamRun with `parent: {run_id, member, task_id}`, `depth: n+1`, its own run directory and substrate namespace (ClawTeam team name = inner run id, created via `spawn-team` with the creating Member as ClawTeam leader, avoiding trap 1).
2. **Delegated task.** The outer task `t` is marked `delegated_to: <inner run id>` and completes only when the inner run reaches a terminal status: the outer task's completion is driven by the inner RunResult, not by the outer Lead.
3. **RunResult.** The inner Lead ends the run by writing `{status: completed|failed|aborted, summary, deliverables[], risks[], archive_ref}` (Hermes' `output_schema` is the precedent [ev:claude-agent-teams-hermes-openbot#F22]). The **result carrier** is layer-owned: the run layer writes the RunResult into the *outer* run's `run.json` (`nested_runs[].result`) and into the inner run's archive; it signals the creating Member with `clawteam inbox send <outer-team> <creating-member> <RunResult summary>` (cross-team send probe-verified [ev:clawteam-probe-log#F19]); and it closes the delegated outer task with `clawteam task update <outer-team> <task-id> --status completed`, optionally with `--description` carrying a one-line pointer to the RunResult path. Message = notification; `run.json` = record; task status = DAG closure. No task-metadata verb exists or is used (walkthrough step 6).
4. **Isolation.** Inner Members get inner-scoped identity and workspace (worktree based on the outer task's branch, not the parent's worktree); messages are delivered only within a run unless an edge crosses the boundary explicitly (creating Member ↔ inner Lead). The contract **declares** `independence.declared: advisory | mechanical` (from the template) and **records** `independence.achieved: namespace | data-dir | mechanical` per nested run (vocabulary per §2): on ClawTeam today `achieved = namespace` — the team name is the only boundary and ClawTeam enforces none between teams [ev:clawteam-probe-log#F19]; `data-dir` when the inner run gets its own `CLAWTEAM_DATA_DIR` (still bypassable by the global `--data-dir` flag on every command [ev:clawteam-probe-log#F2]); `mechanical` requires the inbox-membership-ACL PR or owning the spawn path. The declaration may not exceed what the substrate can achieve without the run layer failing closed (§2).
5. **Archive nesting.** The inner run archives itself; the outer archive records `nested_runs[]` with the inner archive ref; cleanup = stop processes (registry-driven), snapshot, then remove mutable dirs.
6. **Failure propagation.** Inner terminal status ≠ completed → outer task `failed` + message; the run layer watches inner liveness (inner Lead dead with tasks pending → `aborted`).
7. **Leak prevention.** Nothing of the inner run is written to any Assistant or TeamTemplate; inner Ephemeral Assistants stay in the inner archive; harness-side memory is disabled for inner invocations (`--bare`, fresh profile/agent) per `harness-broker-model.md`.

On ClawTeam this is glue code over existing primitives — fit-gap TE-05 CT `Xs!` after the W3 re-score (parent link, result carrier, isolation record and stop-before-cleanup are new code, not configuration; `P` in the legend requires no new code) — plus a layer-owned `run.json`; `created_by` on `TeamConfig`, process-stopping cleanup and `task wait` scoping are the bounded upstream changes. PoC C's pass criteria map to items 4, 3, 5, 7; criterion 1 (isolation) reads: no inner DAG task and no inner *content* message appears in the outer team's tasks/inboxes/events; ClawTeam lifecycle notices (on-exit/idle/join/shutdown message types) addressed to the inner team's leader are excluded by type, and the check is evaluated on the archive's filtered projection recorded by the layer — with `independence.achieved` recorded honestly (`minimal-poc-plan.md` §5); criterion 2 (result returned) is the item-3 carrier.

## 7. Pressure test — long-running operational run (LO-01..LO-04, TE-02)

**Scenario.** A Training Operations TeamRun supervises a 10-day training job (checkpoint every 6 h). Deterministic watchers run throughout; on day 4 the metric poller sees validation loss rise for three consecutive evaluations and the trigger rule fires; Run & Monitor is invoked, interprets (divergence vs noise), decides (roll back to checkpoint N-1, halve the LR), escalates to the user, delegates a config patch to CodeMod, reports; the job continues; Run & Monitor is invoked again at the next checkpoint summary and at any later trigger.

**Walkthrough — what is deterministic and what is an Assistant.** Deterministic Backends (as invocation targets they belong to `harness-broker-model.md`; their run semantics are here): process/job monitor, metric poller, checkpoint detector, scheduler (6-hourly summary), health check (GPU/disk), log parser, trigger-rule evaluator (LO-02). Assistant invocations: interpretation, decision, escalation, planning/coordination, reporting (LO-03). **"Fresh session by default" over 10 days** (TE-02) means: every trigger produces a *new* AssistantInstance — a new HarnessInvocation with fresh context — injected with the Assistant definition plus a compact **RunStateSummary** produced deterministically by the run layer from the archive (job id/phase, last metrics window, checkpoints, prior decisions with one-line rationale, open escalations, pending tasks); no transcript carry-over; resume (`--resume`, OpenClaw same `--session-key`) is an explicit per-invocation opt-in that the previous invocation may request (`resume_hint`) and policy may deny. Surviving host/daemon restarts: the run directory (watcher config, trigger history, decision log, checkpoint pointers, task graph) and idempotent watcher definitions; not surviving: LLM sessions and watcher processes (restarted from definition).

**Walkthrough — substrates.** ClawTeam's model is the inverse: the Worker Loop Protocol tells workers to keep a foreground watch loop and not exit [ev:clawteam-model#F15]; LeaderWatcher polls every 60 s and injects a `scheduler_check` into a *resident* leader pane (an inbox message on the subprocess backend) [ev:clawteam-model#F18]; keepalive re-launches the CLI on clean exit only (exit 0 [ev:clawteam-spawn-platform#F14]) and only for CLIs with a resume argv (none for openclaw/generic [ev:clawteam-spawn-platform#F1]); hooks fire on 18 event types but `HeartbeatTimeout` is never emitted [ev:clawteam-model#F23]; Redis wakeup is best-effort [ev:clawteam-model#F10]; `ContextRecovery` runs only under `harness conduct` [ev:clawteam-model#F20]. The LO pattern is composition — `inbox watch --exec <handler>` or a hook → `clawteam spawn … --no-keepalive --task` — fit-gap P~ [ev:clawteam-model#F19][ev:clawteam-spawn-platform#F4]. The fork adds `trap EXIT` + `respawn_agent` re-running the recorded argv (max 2), an unenforced circuit-breaker model, and documents idle `openclaw tui` timeouts as "accept worker churn" [ev:clawteam-openclaw-fork-delta#F11][ev:clawteam-openclaw-fork-delta#F12][ev:clawteam-openclaw-fork-delta#F29]. OpenClaw is the closest native fit: `openclaw cron add --agent … --session isolated|main --message|--command <shell> --every/--cron/--at --on-exit`, event `triggers`, `webhook`, `failureAlert`, `runLog` [ev:openclaw-native-and-telegram-verification#F9], per-agent `heartbeat` (an `agents.list[]` key [ev:openclaw-native-and-telegram-verification#F13]), one-turn `openclaw agent --session-key` [ev:harness-cli-capabilities-b#F1] — requiring the Gateway daemon and an `agents.list` agent. Hermes: the kanban dispatcher spawns a fresh `hermes -p <profile> --cli … -q <prompt>` per ready task with runtime caps and `task_runs` history; status `scheduled`; `hermes cron` name-verified [ev:harness-cli-capabilities-b#F19][ev:claude-agent-teams-hermes-openbot#F25]. Claude Code: `--bg` sessions are resident; fresh-per-trigger = external scheduler + `claude -p` [ev:claude-agent-teams-hermes-openbot#F17].

**Breakpoints.** L1 Job-level watchers (metric/checkpoint/log/trigger rules) exist in no substrate; every system offers process liveness, generic schedulers and hook/payload slots (G-LO-02). L2 ClawTeam's operational primitives assume a resident LLM; fresh-per-trigger is composition. L3 The RunStateSummary exists nowhere: ClawTeam's recovery prompt is within-run and conductor-only; OpenClaw resume replays the whole session; Hermes memories carry project facts [ev:harness-cli-capabilities-b#F19]. L4 Restart semantics are substrate-specific, never a declarative policy on a Member/TeamRun (G-LO-04). L5 Trigger→invocation wiring that also carries the Assistant definition exists only inside OpenClaw and Hermes (G-LO-03). L6 Both native schedulers need their gateway daemon: `product-intent.md` §1.6 names the OpenClaw gateway (with Telegram and tmux) as a non-prerequisite verbatim; the Hermes gateway is excluded on the same ground by MS-01 "fully useful locally" (G-MS-01) — this document's reading, not §1.6's text.

**Minimal addition — an operational run mode.** `TeamRun.mode: operational` adds: (1) `watchers[]` — deterministic Backends registered as run components, each `{kind, config, schedule|event, trigger_rules, on_trigger: {invoke: <member>, with: run_state_summary, resume: never|opt-in}}`; the resident piece is the host's OS scheduler (cron / launchd / schtasks), which invokes a stateless `ats tick <run>` that re-reads the run directory, re-spawns dead watchers idempotently from their definitions and evaluates trigger rules — neither the LLM nor a long-lived run-layer daemon is resident, which is what lets the run survive a host or daemon restart (`architecture-options.md` §3 "Long-running operational run", §8); (2) a `RunStateSummary` projection (bounded, deterministic, regenerated per invocation); (3) a first-class **decision log** (trigger → invocation → decision → action → outcome) in the archive; (4) a declared restart policy `{watchers: restart, instances: fresh, run_state: durable, resume: opt-in}` (LO-04). The scheduler substrate is pluggable — an OS timer here, OpenClaw cron or Hermes cron where the user already runs that daemon — without changing these semantics.

## 9. Visibility & audit model (TC-04, TE-07, XC-04)

`Member.visibility ∈ {visible, hidden}` is presentation; it never changes capability. Two projections of one roster: the **user-facing view** (local conversation, local UI, Surface) omits hidden Members unless the user opts in — so a hidden Member has no Surface binding unless the user opts in, a modelling consequence of TC-04 visibility together with MS-03 (a visible Bot identity is presentation state bound to a Member), not a requirement authored here; the **archive** lists everything. Every automated action is an archive entry with actor, policy decision and references: Member creation, HarnessInvocation (broker ledger ref), task transitions, messages, nested run create/end, watcher trigger, proposal extraction. Because ClawTeam discards worker output, records `exit_code: null` [ev:clawteam-probe-log#F12][ev:clawteam-probe-log#F14] and its subprocess backend never emits `AfterWorkerSpawn` [ev:clawteam-spawn-platform#F9], the run layer's spawn wrapper captures stdout/stderr and exit code; per-harness sources are Claude `-p --output-format json` (`total_cost_usd`), Codex rollouts (tokens only), Grok JSON [ev:harness-cli-capabilities-a#F10], and Hermes `-z --usage-file` — evidenced for the one-shot form only; `hermes chat` has no `--json`/`--output-format` and whether `chat -q` accepts `--usage-file` is unprobed, so a `chat -q` Member (§4) records `cost_source: unavailable` until that probe runs [ev:harness-cli-capabilities-b#F7] (negative findings, `evidence/harness-cli-capabilities-b.md` §3). Per-system audits (OpenClaw `audit`/`tasks`, Hermes `task_runs`/logs, dsh archive dirs) are referenced, not duplicated.

## 10. Cross-platform execution (TE-08, XC-02)

The run model assumes: no tmux (subprocess backend or direct spawn; ClawTeam `spawn tmux` fails cleanly here and `launch` of a tmux template reports success with zero processes [ev:clawteam-probe-log#F15]); prompt and definition delivered by **file** where the harness allows — Claude `--append-system-prompt-file` (in the docs and the binary, **absent from `claude --help`**; a day-one probe [ev:harness-cli-capabilities-a#F2]), OpenClaw `agent --message-file` [ev:harness-cli-capabilities-b#F1], Grok `--prompt-file` [ev:harness-cli-capabilities-a#F1] — rather than long argv, and never `--task` through `clawteam spawn` (§4): cmd.exe newline truncation is reported for ClawTeam's multi-line `-p` prompt [ev:clawteam-spawn-platform#F20]; exit code and output captured by our wrapper, since ClawTeam's Windows branch has no keepalive and no exit-code env and its default `skip_permissions` hits `os.getuid()` [ev:clawteam-spawn-platform#F20][ev:clawteam-probe-log#F25]; the fork's `platform_compat.py` (subprocess default on Windows, msvcrt locks, `pid_alive`) is the reusable shim [ev:clawteam-openclaw-fork-delta#F19]. **macOS** (named by TE-08): the same POSIX branches (fcntl locks, `os.kill(pid,0)`, the `sh` keepalive wrapper) apply, ClawTeam's CI matrix is `ubuntu-latest` + `macos-latest` only (unit tests, no spawn) and there is **no Windows CI** in ClawTeam or the fork; macOS was not probed here, so it is "documented, unverified" until the macOS smoke of `minimal-poc-plan.md` §6 runs [ev:clawteam-spawn-platform#F20][ev:clawteam-probe-log#F25][ev:clawteam-openclaw-fork-delta#F19]. Host OS and harness availability are recorded per Member at instantiate as independent dimensions (XC-02): `host: {os, arch}` and `harness: {name, version, present}` from the HarnessProfile; gateway-dependent services (OpenClaw cron/`sessions_spawn`, Hermes kanban dispatch) are *optional* substrate services, never prerequisites (OpenClaw gateway per `product-intent.md` §1.6; Hermes gateway by MS-01/G-MS-01, §7 L6).
