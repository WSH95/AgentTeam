# Independent review — M0 + M0.1 at `3407ec9`

## 0. Verdict and how to read this

**Verdict.** The package is unusually rigorous: frozen 54-row register, evidence-pinned fit cells, an architecture panel with two judges, adversarial critics, honest "partial/advisory" labels. Each item cites the document and section **as of `3407ec9`** (`ADM` = `assistant-domain-model.md`, `TEM` = `team-execution-model.md`, `HBM` = `harness-broker-model.md`, `AO` = `architecture-options.md`, `MPP` = `minimal-poc-plan.md`, `HCC-a` = `evidence/harness-cli-capabilities-a.md`). ## 1. Substantive findings

**R1. Answer retained, plan de-authorized → no executable next step.** M0.1 kept the AO §5 answer but stamped every PoC detail "historical / provisional / not approved" (MPP header and §1–§8; product-intent §4; AO §3 banner; README "Current gate"). The nine documents now carry dozens of hedges and a reader cannot tell what is decided. Decided vs provisional should live in one short place (DECISIONS + a design spec), not as caveats sprinkled through ~660 KB. MPP is now half plan, half museum ("Historical …" headings).

**R2. ClawTeam is used against its grain; "thin" understates the coupling.** Evidence at `3407ec9`: upstream HEAD `0119833` unchanged since 2026-05-09 with 22 open PRs (AO §2 O5; reuse §5), `clawteam-mcp` broken by `mcp` 2.0 (probe-log F1), `os.getuid()` on Windows (spawn-platform F20), DEVNULL output and `exit_code: null` (spawn-platform F21; probe-log F14), `launch` swallows spawn errors (probe-log F15), every spawn exit fires `lifecycle on-exit` even on exit 0 (probe-log F14; AO §3 assumption (c)), no hidden flag so two rosters (TEM §5; AO assumption (f)), no spawn gate so TC-05 is bypassable (spawn-platform F16; TEM §5 B3), namespace-only isolation (probe-log F19), cleanup leaves processes (probe-log F20), dangling `blocked_by` ids accepted (probe-log F7), `task update --metadata` does not exist (AO §8). The layer's own operating rules — never `launch`, never `--task`, `skip_permissions=false`, wrapper tee, spawn-on-unblock observer, run-scoped `CLAWTEAM_BIN`/PATH shim, stop-before-cleanup, id validation (AO §3, §5; MPP §4) — are roughly ten workarounds. ClawTeam's execution model is a resident leader plus resident polling workers (TEM §7 "ClawTeam's model is the inverse"); the product's lifecycle principle is fresh one-shot instances plus deterministic glue (brief §1, §8; TE-02). What ClawTeam contributes to PoC B/C after the workarounds: a file task DAG with auto-unblock and `task wait`, file inboxes, a pid registry, worktrees, snapshot, and its coordination SKILL text — which is what panel dissent 3 prices at ~300 lines MIT (AO §4). The documents defer the decision to PoC B (AO §6 risk table); that is acceptable only if the CoordinationSubstrate seam is designed from the run layer's needs and proven by a second, trivial, local implementation first — otherwise the seam will be ClawTeam-shaped and the advertised "one-implementation swap" is illusory. Judge 1's required sentence "'independent' means format-independent, not substrate-free" never landed in AO. *Owner decision 2026-08-23: defer + measure (local deterministic substrate first, ClawTeam CLI adapter second, written exit criterion before PoC B).*

**R3. The "smallest layer" first slice carries objects no PoC falsifies.** AO §5.1 admits the AR manifest/lock/report and the Proposal/overlay path are "built, not falsified by any PoC". For a smallest-layer PoC they belong *outside* the first slice (keep only the effective-definition hash hook). The overlay resolver inside the PoC-A slice (assumption (i)) is YAGNI for a single-owner PoC — ADM §13 Q1 asks exactly this.

**R4. Grok Build as a *required* first-pass harness enlarges PoC A.** The brief's PoC A is Codex + Claude Code (brief §17). Grok's value is as the HB-08 test ("new harness = adapter-only change"): sequencing it third, after the seam settles on two adapters, with "adapter-only diff" as its acceptance criterion would keep PoC A small. Grok's active auth is unverified (M0.1 F2) and its flags are partly undocumented (HCC-a §5). *Owner decision 2026-08-23: keep all three required (M0.1 F3 stands); this finding stays recorded as a dissent; Grok's probes become day-one blockers.*

**R5. Tier 0 (deterministic no-op harness) is parked as an open question (Q8) — it should be the backbone.** ATM's lesson that LLM end-to-end evidence is flaky and costly (legacy-atm §4 R11), credential-free CI (M0.1 F5) and ToS-sensitive subscription use (R8) all point the same way: the deterministic tier is the primary automated test surface on all three OSes; live Tier-1 runs are attended, budget-capped acceptance evidence on the owner host, recorded in the ledger. *Owner decision 2026-08-23: Tier 0 automated/CI precondition; Tier 1 attended acceptance and the only tier that can PASS.*

**R6. The PoC B orchestration model is undecided in a way that matters.** MPP §4 runs the Lead as one long headless invocation; TEM §13 Q2 (as numbered in MPP §8 open question 2) asks whether it may be re-invoked fresh per DAG event. The product principle (fresh instances; deterministic components do the waiting) and the tool-call-compliance risk (ATM U2 0/2, atm-salvage F24) both argue for: the run layer is the deterministic event loop; the Lead is invoked fresh per decision point with a RunStateSummary (exactly the TEM §7 operational design). This further shrinks what any coordination substrate must provide.

**R7. Register rule violated on HB-03.** `product-intent.md` (frozen; "the only place requirements are authored") states precedence user > Assistant > default; README, the AO §5 answer, ADM §7 and HBM §5 state user > Assistant > **team** > default ("a modelling choice consistent with both IDs"). Also unresolved: whether a team-level *constraint* (independence: reviewer ≠ implementer harness) should bind above an Assistant preference. Fix: register v3.4 amends HB-03 explicitly, or the glossary states it.

**R8. Subscription OAuth for unattended runs is recorded as settled (Q5) but is ToS-sensitive.** HCC-a §4 notes the xAI/OpenAI automation terms "remain unverified beyond the vendor docs". Fine for owner-operated PoC runs; keep it a living risk with a re-check date, and design the ledger so attended vs unattended and native vs api-test are always distinguishable.

**R9. The user-facing shape is under-specified.** Brief §1.6 ("pick an Assistant or TeamTemplate; point it at a repo; get a fresh run; see the archive; accept or reject proposals") maps to one line of CLI verbs (`ats assistant/template/run/member/nest/result/archive`, AO §5 table) and a SKILL.md mention. There is no component diagram, no on-disk layout, no record schemas in one place, no CLI UX sketch. The implementing phase needs a 3–5 page design spec; the rename to `atm` makes CLI design near-term.

**R10. Naming collision.** CLI `atm` vs legacy "ATM" (agent-team-manager): DECISIONS 0002 and every document use "ATM" for the demoted project. Adopt a convention now ("legacy ATM" vs `atm` CLI / AgentTeam) and check distribution-name availability (PyPI/npm) before committing to `atm` as a package name.

**R11. Brief §17/§19 "Do not write a large implementation plan yet. Define small experiments." is violated in effect.** The corpus is ~1.2 MB / 51 files; AO §5 is a build plan in all but name (ten-row component/LOC table, two seams with method lists, CLI verb list, slice order, nine-PR upstream backlog, a 12-month maintenance contract). M0.1 mitigated by relabelling ("historical/provisional"), not by reducing. Meanwhile the brief's *primary product object* — the Assistant definition — gets about two pages (ADM §3–§4), "illustrative, not a schema". The centre of gravity is substrate archaeology, not the product object.

**R12. PoC A as sketched is undersized on the three axes that define the product** (MPP §3): (i) the definition under test carries **one** vendored Skill, so Assistant ≠ Skill (AD-09, M) is not visibly exercised — the brief's own example is a three-Skill composition (brief §2); (ii) everything runs on **one host**, so "portable" (AR-03, M) never crosses a host boundary — a credential-free export → import → validate-hash round-trip on another CI OS would test it deterministically; (iii) behavioural consistency ("the same reviewer colleague giving consistent judgment", product-intent §1.7) is informational only ("planted-defect recall" is not a pass criterion) — PoC A can PASS with two unrelated reviews. Proposed: keep the mechanical criteria as the architecture gate and add a reported semantic tier (planted-defect recall per harness) that gates "product-useful", not "architecture".

**R13. Brief §14's second clause ("avoid embedding a heavy dependency merely to obtain one small feature") never became a register row**; only "avoid reinventing mature infrastructure" did (XC-03). It is precisely the clause that bites on the ClawTeam pin (R2). Make it an explicit criterion for the M2 ClawTeam decision (or a register row XC-05).

**R14. TeamTemplate evolution is asserted but not modelled.** EV-03 names "Assistant/TeamTemplate"; only the Assistant overlay model exists (ADM §9). Fine to defer; record it as a known gap.

**R15. User-specific preferences** (brief §1: "stable user-independent *or user-specific* working preferences") are forced into the User Overlay (ADM §3 comment, §9 table); ADM §13 Q1 asks whether a single owner needs overlays at all. For a first slice: keep `preferences` in the Base; user-level choices arrive as run flags (already PoC A Run 2); introduce overlays when sharing/evolution arrives.

**R16. "Run" is overloaded against the glossary** (glossary: "run" reserved for TeamRun; MPP §3 uses Run 1/2/3 for solo invocations; AO §5 "solo runs"). Cleanest fix for the CLI: a solo execution *is* a TeamRun with one Member and no coordination substrate — one record model from the first slice onward (HBM §7 already half-says this: "`run_id` is the TeamRun id, or the solo-run id").

**R17. Long-running operations (brief §8) are demoted to S priority and deferred after PoC C** (AO §5 sequencing notes; MPP §1), although the brief gives §8 equal weight and LO needs no team substrate (deterministic tick → fresh `direct` invocation + RunStateSummary, TEM §7). If training operations were the first real use, an "operational mode on the direct path" slice would belong before any team substrate. *Owner answer 2026-08-23: code/dev teams first → operational mode stays after PoC C.*

**R18. "Owner" in the documents means the orchestrating *session*, not the human owner.** DECISIONS 0006: "the owner (this session) writes the glossary, requirement register … tiebreaks the panel, and performs the final read-through". Hence `evidence/panel/owner-tiebreak.md` ("role: session owner tiebreak note"), the fix-pass decisions D1–D15, and AO §5.0 "Owner assumptions adopted (verbatim; owner-authored)" — assumptions (a)–(l) — were **agent-authored in the owner's voice**; the completeness critic flagged exactly this ("a reviewer cannot tell what the owner actually decided versus what the synthesis decided in the owner's name", `critics/completeness.findings.md`). The M0.1 decisions (Q2/Q3/Q5/Q7, harness set, ATM reuse) are distinguishably the human owner's; (a)–(l) are not. *Owner decision 2026-08-23: (a)–(l) are historical, session-authored panel inputs, not owner decisions; later plans restate what they need.*

DECISIONS 0009 (D7) is silently reversed by M0.1 F9.** D7 bound the fit-gap to "'hidden' is the TC-04 row's concern only — AD-07/TE-04 score the ability to create a temporary member"; F9 restored hidden-if-desired into AD-07 and the matrix now implements that (fit-gap Method; AD-07 row).
